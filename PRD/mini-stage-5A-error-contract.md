# PRD: мини-этап 5A — контракт ошибок и наблюдаемость API

Мини-этап выделен из бэклога этапа 5 (2026-09-23). Собраны девять пунктов, которые до этого
существовали как разрозненные строки `fwd-17`…`fwd-25`: у них одна тема (что видит клиент при ошибке и
что видит оператор в логах), один общий механизм (`kernel.exception`-listener) и одна цена ошибки
(несогласованный контракт API сложно менять потом).

## Зачем

Сейчас контракт ошибок сложился стихийно и в четырёх местах это уже не «долг», а **дефекты**:

- `fwd-20` — `CollectionController::list` не валидирует пагинацию: `?limit=abc` молча отдаёт пустой
  список вместо `400`. Клиент видит «данных нет» вместо ошибки запроса.
- `fwd-25` — не-строковый `owner` (`?owner[]=x`) молча игнорируется: управление падает в ветку «свои
  коллекции», и клиент получает правдоподобный, но неверный результат вместо `400`. Тот же класс, что и
  `fwd-20`.
- `fwd-21` — три `catch (\Throwable)` в `CollectionController::create/update/delete` возвращают `500`
  без записи в лог (monolog не подключён, поэтому `LoggerInterface` не резолвится как аргумент
  контроллера; после подключения бандла он инжектируется обычным конструкторным autowiring).
  Сбой на этих маршрутах невозможно диагностировать.
- `fwd-19` — два разных тела `401` в зависимости от того, кто отклонил запрос: jwt-entry-point Lexik
  (`{"code":401,"message":"JWT Token not found"}`) или guard в `AbstractApiController`
  (`{"error":"Unauthorized"}`).

Остальные пять — согласование уже принятых решений: `fwd-17` (ручные JSON-403 вместо listener),
`fwd-22` (два лейбла `error` на статус 422), `fwd-24` (нестабильные `details`), `fwd-23` (дублирование
схем ошибок в OpenAPI), `fwd-18` (две URL на удаление комментария).

`fwd-18` — смежный, а не про конверт: он про каноническую поверхность маршрута. Включён потому, что
правит тот же контроллер и ту же тему «согласованность контракта до первого внешнего клиента»; если при
разбивке на PR он мешает, выносится отдельной строкой этапа 5.

## Границы

**Входит:** единый конверт ошибок для 400/401/403/404/409/422, единый механизм их построения
(`kernel.exception`-listener + entry point), логирование `500`, валидация пагинации, схемы ошибок в
OpenAPI, решение по двум DELETE-поверхностям комментария.

**Не входит:** изменение успешных ответов, новые эндпоинты, логика авторизации (правила доступа
остаются как в 5.10), перевод сообщений, продуктовые изменения гостевого доступа (`fwd-7`).

## Порядок работ

1. **`fwd-20`** и **`fwd-25`** — оба про `CollectionController::list`: пагинация через `parsePagination`
   (`?limit=abc → 400`) и не-строковый `owner` → `400` вместо молчаливого игнорирования. Самые дешёвые и
   самые явные дефекты; трогают один контроллер.
2. **`fwd-19`** — единый 401-конверт: кастомный entry point / failure handler Lexik, примеры 401 в
   OpenAPI (они уже описывают желаемую форму — `error` + `message` — поэтому ответ Lexik приводится к
   ним, а не наоборот).
3. **`fwd-17`** — `AccessDeniedException` → JSON listener: убрать ручные 403-блоки.
4. **`fwd-21`** — логирование `500` в listener'е (`['exception' => $e]`, тело без `message`) + покрытие
   трёх локальных `catch (\Throwable)` в `CollectionController`.
5. **`fwd-22`** — единый словарь лейбла `error` для 422.
6. **`fwd-24`** — стабильные `details` при ошибках ввода.
7. **`fwd-23`** — `$ref` на общие схемы ошибок в OpenAPI вместо inline-блоков.
8. **`fwd-18`** — каноническая DELETE-поверхность комментария.

Шаги 2–4 делят один listener/entry point — их логично делать подряд, иначе listener придётся
переписывать дважды. Шаги 5–7 — правки контракта и документации поверх готового механизма.
**Перед шагом 2** зафиксировать каноническую форму конверта (решение 5): `fwd-19` задаёт её для всех
остальных, и без неё шаги 5–6 придётся переделывать.

## Решения, которые нужно принять по ходу

1. **Словарь 422** (`fwd-22`): один лейбл на статус (`'Validation failed'` для всех) или доменные
   категории; если split остаётся — зафиксировать в `ARCHITECTURE.md`.
2. **Стабильность `details`** (`fwd-24`): оставить best-effort `$exception->getMessage()` с фиксацией в
   `ARCHITECTURE.md` или выводить стабильные фразы на уровне call-site (`'Invalid limit'` и т.п.).
3. **Какая DELETE-поверхность канонична** (`fwd-18`): вложенная (`/api/items/{itemId}/comments/{id}`)
   или плоская (`/api/comments/{id}`); вторую — deprecated и снять в следующем мажоре. Внешних
   клиентов нет, решение свободное.
4. **Где логировать** (`fwd-21`): снять локальные `catch` и отдать всё listener'у или логировать на
   месте. Предпочтение — первый вариант (один источник правды), но он меняет поведение трёх маршрутов.
5. **Канонический вид конверта** (`fwd-19`, `fwd-22`, `fwd-24`): `{error, message, details?}` или
   `{code, message, details?}`. Сейчас Lexik отдаёт `{code, message}`, guard — `{error, message}`, а
   listener'а ещё нет; без фиксации формы три пункта разъедутся. **Решить до старта `fwd-19`** — это
   вход для остальных.
6. **Анонимный отказ: 401 или 403** (`fwd-17`): Symfony бросает `AccessDeniedException` и для
   неаутентифицированного, и для недостатка прав; сейчас анонимного перехватывает entry point Lexik и
   отдаёт 401. Listener обязан различать эти случаи, иначе анонимный отказ станет 403. Закрыть в
   рамках `fwd-17`.
7. **Порядок проверки query-параметров** (`fwd-20` задал первый случай): ошибки пагинации сообщаются
   раньше ошибок `owner` (`CollectionController::list`), а в `ItemController` фильтры разбираются до
   пагинации. Единого правила нет — закрепить одно (например «сначала структурные параметры
   (`limit`/`offset`), затем доменные») и применять при добавлении новых query-параметров, чтобы
   приоритет не оставался молчаливым.
8. **Не-массивные скалярные query-параметры** (`fwd-25` — точка отсечения): в редакции от
    2026-09-26 это читается иначе, чем писалось. `?owner[]=x`, `?name[]=x`, `?search[]=x` **не** тихо
    отбрасываются: `InputBag::get()` бросает `BadRequestException` раньше любого `is_string`, и клиент
    уже получает 400 — но фреймворковой HTML-страницей, а не конвертом API. Поэтому обязателен `400`
    нашим конвертом везде, а не только для `owner`: fwd-25 закрыл `owner` + `name` + `search` разом,
    а также `?limit[]`/`?offset[]` и скалярный `?tags` той же разводкой `all()` вместо
    `get()`/`all($key)` (подробности и эмпирика — `PRD/fwd-25-non-scalar-query-params.md`).
    Политика: параметры, меняющие **идентичность** результата, отвергаются с `400` нашим конвертом;
    фильтры-сужатели отвергаются так же — третьего поведения «тихо игнорировать» больше нет.

## Критерии приёмки

- [ ] Один конверт `401` независимо от точки отказа (entry point и guard дают одинаковое тело).
- [ ] Ручных 403-блоков в контроллерах нет: `AccessDeniedException` конвертируется listener'ом.
- [ ] Один словарь лейбла `error` на статус `422` (или split зафиксирован в `ARCHITECTURE.md`).
- [ ] `details` либо стабильны, либо явно помечены как best-effort в `ARCHITECTURE.md`.
- [ ] Ни один `500` не остаётся без записи в логе (включая три сайта в `CollectionController`:
      `POST`/`PATCH`/`DELETE` на коллекциях оставляют след в логе).
- [ ] `?limit=abc` и `?limit=0` дают `400`, покрыто тестом.
- [ ] `?owner[]=x` (не-строка) даёт `400`, а не молчаливую подмену на свои коллекции.
- [ ] Схемы ошибок в OpenAPI — `$ref` на общие компоненты, без inline-дублей.
- [ ] Для комментария объявлена одна каноническая DELETE-поверхность, вторая помечена deprecated.
- [ ] `composer ci:all` зелёный; smoke-скрипт покрывает изменённые коды ошибок.
