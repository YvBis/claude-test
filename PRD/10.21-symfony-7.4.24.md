# 10.21 — Security-бамп Symfony `7.4.23` → `7.4.24`

## Дефект

`main` покраснел на блокирующем `Dependency Audit` сразу после мержа #206 — не из-за кода. 2026-11-25 Symfony опубликовал **15 advisories в 8 пакетах**, все закрыты в **`>=7.4.24`**; после 10.17 мы на 7.4.23.

| Пакет | Advisories | Ключевое |
|-------|-----------|----------|
| `symfony/framework-bundle` | 3 | CVE-2026-133762 (без `APP_RUNTIME_MODE` CLI-воркеры отдают полные дампы исключений), CVE-2026-133747 (scoped HTTP-клиент с кэшем шлёт креды на любой origin), CVE-2026-133745 (редирект с `//` уводит на чужой хост) |
| `symfony/http-client` | 4 | кэш делит ответы между пользователями при `withOptions()`, credential-семантика |
| `symfony/routing`, `symfony/serializer` | по 2 | host/path-обработка, десериализация |
| `symfony/doctrine-bridge` | 1 | CVE-2026-133759: remember-me принимает просроченные токены после logout — **у нас remember-me не используется** |
| `symfony/http-kernel`, `security-core`, `security-http` | по 1 | ядро/сессии |

## Решение

Только `composer.lock`: `composer update "symfony/*" --with-dependencies`. `composer.json` не меняется — констрейнт `^7.4` уже допускает 7.4.24, правка была бы шумом.

Фактически обновились **37 пакетов**:

- 33 `symfony/*` → 7.4.24 (часть поднималась с 7.4.8/7.4.22 — они просто не попадали в предыдущие волны бампов). Остальные 12 `symfony/*` остались ниже (clock, dotenv, password-hasher, flex и т.д.): свежего тега, удовлетворяющего глобу, нет, и advisories их версий не касаются — проверено по базе advisories;
- `symfony/phpunit-bridge` 8.1.10 → 8.1.12 (та же волна, ветка 8.1);
- три не-Symfony минора: `doctrine/deprecations` 1.1.6 → 1.2.0 и `monolog/monolog` 3.12.1 → 3.13.0 подтянуты `--with-dependencies`, а `symfony/polyfill-php85` 1.43.0 → 1.44.0 попал под сам глоб `symfony/*`.

Все — patch/minor в пределах существующих констрейнтов, новых пакетов нет. Транзитивные миноры оставлены, а не откачены вручную: ручной откат означал бы держать lock в состоянии, которое `composer update` тут же пересоздаст.

## Почему отдельная задача

Третий security-инцидент за три недели (10.17 — Symfony 7.4.20 → 7.4.23, 10.20 — Twig, 10.21 — Symfony 7.4.23 → 7.4.24). Смешивать с функциональной задачей нельзя: PR трогает один lock-файл, и в диффе 10.13 это выглядело бы как случайный апдейт.

## Проверки

- `composer audit` — **No security vulnerability advisories found**.
- `composer show symfony/framework-bundle` — `v7.4.24`.
- `ci:all` — полный прогон.
- `composer.json` в диффе отсутствует.

## Заметка к деплою

7.4.24 меняет расположение файловых сессий: #68162 «Use the share directory for file sessions». У нас `framework.yaml:9` держит `handler_id: null`, то есть нативные файловые сессии, поэтому при выкатке активные сессии один раз инвалидируются (файлы переезжают в `%kernel.share_dir%`). Тесты не задеты: в test-окружении `storage_factory_id: session.storage.factory.mock_file` (`framework.yaml:39-40`). Это разовое следствие релиза, а не дефект правки — записано, чтобы выкатка не выглядела «сбросом логинов».

## Наблюдение
Частота волн растёт: два инцидента за сутки (Twig 24.11, Symfony 25.11). Кандидат на автоматизацию вынесен строкой `fwd-37` (Dependabot security-updates, группировка, авто-мерж только для строго lock-only диффа).
