# 10.2 — Расхождение email-валидации: 500 вместо 422

## Дефект

DTO проверяли адрес через `Assert\Email(mode: 'html5')`, домен `Email::fromString` — через `filter_var`. Множества не совпадают: html5 принимает точечную локальную часть (`a.@example.com`, `.a@example.com`), `filter_var` — нет. Такой адрес проходил валидацию, доходил до сервиса, бросал `InvalidArgumentException`, а контроллеры его не ловили (`RegistrationController:79-90`, `LoginController:80-93`) → **голый 500** `{"error":"Internal Server Error"}`.

Три входа: `POST /api/register` (`RegistrationService:30`), `POST /api/login` (`AuthenticationService:25`), `POST /api/admin/users` (`Admin\UserController:81` → тот же `RegistrationService::register`).

**Поправки к первичной формулировке аудита (проверено):**
- `a@b` **не** расходится: `EmailValidator` PATTERN_HTML5 требует точку в домене (`vendor/symfony/validator/Constraints/EmailValidator.php:30`), поэтому он и так даёт 422. В матрицу не входит.
- админский путь идёт через `RegistrationService`, а не через `UserService` — Email там не участвует.
- trim-асимметрии нет: DTO тримит и приводит регистр в конструкторе до валидации (`RegisterUserDTO:36`), валидатор пробелов не видит.

## Решение

Новый constraint `App\Application\Common\Validation\StrictEmail` + `StrictEmailValidator`, который **делегирует домену**:

```php
try { Email::fromString($value); }
catch (\InvalidArgumentException) { $this->context->buildViolation($constraint->message)->addViolation(); }
```

Почему так, а не копия `filter_var`:
- одно правило на DTO и домен: ужесточение `fromString` автоматически подхватывается, расхождение не может возникнуть снова;
- сообщение фиксированное (`Invalid email format`) — доменное `Invalid email: %s` эхом отдаёт ввод, что запрещено D11;
- `null`/`''` пропускаются (их отдаёт `NotBlank`), не-строка → `UnexpectedValueException` (вендорное поведение; на практике недостижимо, свойство типизировано).

Заменено в `RegisterUserDTO:21`, `CreateUserDTO:22`, `LoginUserDTO:15`. Домен `Email.php:17` не тронут: доменные `Assert\*` инертны (валидатор ходит только в DTO), а импорт Application-constraint в Domain инвертировал бы зависимость. Решение зафиксировано здесь, чтобы его не «починили» следом.

## Принятые ограничения

- Конструктор `StrictEmail` принимает только именованные аргументы (`message:`, `groups:`, `payload:`), не options-массив. YAML/XML-маппинг валидаторов в проекте не используется, поэтому латентно; при переходе на него конструктор расширяется.
- Ветка «не-строка» удалена как недостижимая: свойства DTO типизированы, неверный тип отсекает сериализатор (400) до валидатора. Оставлен только instanceof-guard для аргумента constraint.
