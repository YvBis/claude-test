## Почему скелет `Default` (id 18929859) нельзя было включать как есть

Состояние на входе (2026-09-25, `GET /rulesets/18929859`):
- `name: "Default"`, `enforcement: "disabled"`, `target: "branch"`;
- `rules`: только `deletion`, `non_fast_forward`, `pull_request` — **правила `required_status_checks` нет**;
- `conditions.ref_name`: `{ include: [], exclude: [] }` — пустой include невалиден (`Invalid target patterns: ''`), полагаться на него нельзя;
- `GET /rules/branches/main` → `[]` — ни одно ruleset-правило на `main` не действовало, вся защита была классической.

Наивное «включить и удалить классику» молча сбросило бы оба required-чека и `enforce_admins` — защита стала бы **слабее** текущей. Поэтому conditions и checks заданы явно.

Дополнительно: `enforcement: "evaluate"` недоступен вне GitHub Enterprise (репо личное, `owner.type: User`) — поэтапного rollout не существует; порядок только «активный ruleset → проверка → удаление классики», без окна «ничем не защищено».

## S1. Применённый ruleset (`PUT /rulesets/18929859`, переименован в `main-protection`)

```json
{

  "target": "branch",
  "enforcement": "active",
  "bypass_actors": [
    { "actor_id": 97064979, "actor_type": "User", "bypass_mode": "pull_request" }
  ],
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "required_status_checks", "parameters": {
        "required_status_checks": [
          { "context": "OpenRabbit Review", "integration_id": 15368 },

        ],
        "strict_required_status_checks_policy": false,

```

Паритет с классикой, ключ-к-ключу (проверен синьором против живого API): `deletion` ↔ `allow_deletions: false`, `non_fast_forward` ↔ `allow_force_pushes: false`, оба контекста + `integration_id: 15368` + `strict: false`, `count: 0` и все флаги `pull_request`. Пропуски — не пробелы: `required_signatures` выключен и в классике; `lock_branch`/`allow_fork_syncing` в ruleset API не моделируются; `required_linear_history` и `required_review_thread_resolution` оставлены `false` осознанно (5.18).

**Единственное намеренное ослабление — `bypass_actors`.** Классика с `enforce_admins: true` не давала обхода никому; теперь у владельца (`YvBis`, id 97064979) есть обход **только на PR** (`pull_request`, не `always` — прямой push в `main` мимо PR по-прежнему невозможен). Это opt-in: закрывает реальную боль залипшего OpenRabbit (пример — PR #94, где NIM-фолбэк упал с `UND_ERR_HEADERS_TIMEOUT` и понадобился ручной rerun), не выключая защиту целиком. `OrganizationAdmin` в личном репо неприменим — только `User` с `actor_id`. Обход виден в таймлайне PR и в audit-логе репозитория (ruleset-история уровня Enterprise в личном репо недоступна — это утверждение не заявляется).

Порядок применения (ровно так и было):
1. `PUT` с `enforcement: "disabled"` — ответ повторил `bypass_actors` как отправлено: форма валидна, ничего не включено. Техническая деталь: `gh api --input` с файлом, записанным PowerShell `Set-Content -Encoding UTF8`, падает с `Problems parsing JSON` — файл пишется с BOM; писать через `[IO.File]::WriteAllText(path, json, UTF8Encoding(false))` (прецедент из #9: inline-ответы боту).
2. `PUT` с `enforcement: "active"` → `GET` для сверки.
3. `GET /rules/branches/main` — 4 типа правил, все с `ruleset_id: 18929859`.
4. Только потом `DELETE /branches/main/protection` (классика возвратила 404 на последующий GET — удалена).

## S3. `ci-summary`: grep → `toJSON(needs)` + jq

Заменён блок `.github/workflows/ci.yml:263-277`. Старый код:

```bash
STATUS="${{ needs.static-analysis.result }} ${{ needs.unit-tests.result }} ${{ needs.dependency-audit.result }}"
if echo "$STATUS" | grep -q "failure\|cancelled"; then exit 1; fi
```

Две дыры, обе закрыты:
1. **Греб по подстроке пропускал `skipped`.** Результат `skipped` не содержит ни `failure`, ни `cancelled` — job докладывал «All jobs passed». Теперь любой результат кроме `success` (включая `skipped`, `cancelled`) роняет шаг. Это намеренное ужесточение.
2. **Двухточечная хрупкость** (комментарий `ci.yml:259-262`): новый job надо было вписать и в `needs:`, и в строку `STATUS`. Теперь `needs:` — единственное место правки: таблица строится из `${{ toJSON(needs) }}`, новый job попадает в гейт автоматически.

Ловушка, которую нашёл синьор на ревью плана: `done < <(jq ...)` — отказ `jq` давал бы ноль итераций и ложный зелёный (тот же класс тихой дыры). Поэтому `table=$(jq ...) || exit 1` отделён от цикла. `jq` предустановлен на `ubuntu-latest`, `needs` разрешён в job-level `env`, `<<<"$NEEDS_JSON"` закавычен (имена job'ов контролируемы, инъекции нет), shell по умолчанию `bash -e` — process substitution валиден.

Guard: `tests/Infrastructure/Ci/SymfonyLspConfigTest.php::testCiSummaryDerivesGateFromNeedsContext` — блок `ci-summary` содержит `toJSON(needs)` и не содержит интерполяций `needs.*.result`. Проверка добавлена в файл, уже владеющий утверждениями про `ci-summary` (не новым файлом). Существующий пин `:83-84` (в `ci-summary` нет пилота) не тронут и остаётся валидным.

Локальная проверка: YAML валиден (`lint:yaml` OK), guard-тест `SymfonyLspConfigTest` 7/7, логика цикла прогнана на четырёх комбинациях (success→0, failure/skipped/cancelled→1). Полный end-to-end — прогон CI на PR задачи.

## Границы (перенесено из 5.18, действует и для ruleset)

- `OpenRabbit Review` стартует на `opened`/`synchronize`/`ready_for_review`; reopen без push оставляет чек pending — мерж блокирован до push.
- Отменённый (`cancel-in-progress`) или упавший по таймауту прогон вердикта не даёт и блокирует мерж: «нет вердикта = не одобрено».
- Обход: «Merge with bypass» на конкретном PR (вместо прежнего `DELETE /branches/main/protection`); виден в таймлайне PR и audit-логе.

## Что осознанно не входит

- `allowed_merge_methods` оставлены все три (паритет с классикой), хотя проект работает squash-only. Запрет merge/rebase — отдельное процедурное решение, не харнесс 5.27.
- `required_linear_history`, `required_review_thread_resolution`, `required_signatures` — не добавлялись (паритет; последнее — отдельная задача, как и в 5.18).
