# 10.9 — Bulk-удаление документов из индекса

## Дефект

`CollectionService::delete` и `UserService::deleteUser` удаляли поисковые документы по одному: цикл `removeItem()` на каждый айтем. Удаление коллекции или пользователя с 1000 айтемов — 1000+ HTTP-вызовов в Meilisearch после коммита. Счётчики при этом сходятся, поэтому дефект не виден функционально: он в стоимости.

## Решение

1. **Порт.** `SearchIndexerInterface` получает `removeItems(array $ids): void` и `removeCollections(array $ids): void` (`list<ItemId>` / `list<CollectionId>`). Пустой список — no-op по контракту: пустая коллекция легальна, поэтому сервисы передают собранные id безусловно, без `if`.
2. **Сервисы.** `CollectionService::delete` — один `removeItems($itemIds)` вместо цикла; `removeCollection($collectionId)` остаётся (один документ). `UserService::deleteUser` — один `removeItems($itemIds)` + один `removeCollections($collectionIds)`, по-прежнему после `transactional()`. `ItemService::delete` не тронут: там одиночный путь.
3. **Адаптер.** Оба метода вызывают `deleteDocuments($ids)` — vendor `delete-batch` (`vendor/meilisearch/meilisearch-php/src/Endpoints/Delegates/HandlesDocuments.php:174-187`). Вызов остаётся внутри `write()`, поэтому fail-open и circuit breaker считают один раз на bulk-вызов.
4. **Маппинг VO → строки обязателен.** `deleteDocuments()` не валидирует элементы, в отличие от `deleteDocument()`. Объект `ItemId` сериализуется в `{}`, движок отвечает 202 и роняет таск асинхронно — `write()` этого не видит, удаление молча не происходит. Поэтому `array_map(… ->toString(), $ids)` и контрактный тест на тело запроса.
5. **Пустой список не доходит до движка.** Vendor пропускает `[]` в delete-batch без проверки; поведение пустого batch на v1.55 не проверялось. Ранний `return` в адаптере — несущая защита, закреплён тестом «ноль запросов».

## Отклонение от формулировки Roadmap

Roadmap просил «один filter-delete на вызов». Реализован batch по ids, потому что:

- id уже собраны до `remove()` ради cascade-orphan (паттерн 6.5) — фильтр не экономит ни одного запроса к БД;
- `UserService` удаляет документы в двух индексах (`owner_id` в items, `owner_id` в collections) — фильтр не даёт выигрыша в единообразии;
- ошибка в строке фильтра даёт зелёный таск, который ничего не удалил; ids детерминированы.

Acceptance переформулирован: «одна задача индекса на вызов, счётчики сходятся».

## Изменение гранулярности отказа

Раньше падение движка посреди цикла оставляло часть документов удалёнными. Теперь один неудачный bulk-вызов оставляет все N документов до `search:reindex`. Fail-open не изменился, но радиус одного проглоченного сбоя вырос с 1 до N, а `ItemReindexer` не чистит документы удалённых строк. Записано в AssumptionLog как принятый риск.

**Follow-up (не в скоупе):** `ItemReindexer::walk` индексирует по одному документу — fan-out переименования коллекции всё ещё стоит ~1000 HTTP. Кандидат `indexItems(array)`.

## Тесты

- `CollectionServiceTest`: `removeItems` ровно один раз с полным списком id, порядок `['findIds','remove','flush','removeItems','removeCollection']`; путь удаления без айтемов передаёт `[]`; `testFlushFailureLeavesTheIndexUntouched` расширен новыми методами.
- `UserServiceTest`: `removeItems`/`removeCollections` по одному разу с аргументами; never-список в `testBlockDeactivates` дополнен.
- `MeilisearchSearchAdapterTest`: delete-batch URL, тело — список строк (не VO и не `{"ids":…}`), пустой список → ноль запросов, ошибка движка проглатывается с одним логом.
- `MeilisearchEngineAcceptanceTest`: 5 айтемов и 3 коллекции индексируются, bulk-удаляются, счётчик сходится к нулю (ожидание по `stats()`, таски асинхронны).

**Красное доказательство:** возврат цикла в `CollectionService::delete` → `removeItems` не вызван, тест порядка падает.

## Проверки

`ci:all` зелёный; целевые прогоны — сервисные, контрактные и engine-acceptance тесты.
