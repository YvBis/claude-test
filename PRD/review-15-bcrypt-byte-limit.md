# review-15 — bcrypt: 72 байта, а не 255 символов

`password_hash(..., PASSWORD_BCRYPT)` читает не больше 72 байт пароля и молча
отбрасывает остальное (php-src `crypt_blowfish.c`, `BF_set_key` заполняет 18 слов
по 4 байта). DTO разрешали 255 **символов**, поэтому стобуквенный пароль
регистрировался с кодом 201, но верифицировался только по первым 72 байтам: два
разных пароля с общим 72-байтным префиксом открывали один аккаунт.

## Решения

### D1. 72 — доменный инвариант, а не продуктовый лимит

`PasswordHash::BCRYPT_MAX_BYTES = 72`. В отличие от `MAX_PLAIN_LENGTH = 255`
(продуктовая граница, живущая только в DTO), это свойство самого bcrypt, поэтому
проверка стоит и в `createFromPlain`. Докблок `MAX_PLAIN_LENGTH` теперь прямо
отсылает к новой константе, чтобы два числа не путались.

Граница — ровно 72, не 71: версия php-src из PHP 8.3 не требует NUL-терминатора
внутри буфера, ограничение в 71 байт относится к реализациям, которые его требуют.

### D2. Второй `Assert\Length`, а не замена первого

```php
#[Assert\Length(min: 8, max: 255, ...)]                                  // кодовые точки
#[Assert\Length(max: BCRYPT_MAX_BYTES, countUnit: Length::COUNT_BYTES)]  // байты
```

Два ограничения, а не одно: минимум остаётся в символах, чтобы не ослабить
короткие multibyte-пароли сменой единицы. Symfony выполняет оба (`LengthValidator`
считает `\strlen` для `COUNT_BYTES`; остановки на первом провале нет, кроме
`GroupSequence`), поэтому при 300 байтах в `details` попадут оба сообщения, при
73 — только байтовое.

В Symfony 7.4 нет `CountUnit`-энума — единица задаётся строкой
`Length::COUNT_BYTES`. Это проверено по вендору, а не по документации.

### D3. NUL-байт — отдельная дыра, закрытая здесь же

Пароль с `\0` проходил обе проверки длины, после чего `password_hash()` бросал
`ValueError` (не `HttpException`) → **голый 500**. Комментарий в домене
(«`password_hash()` with hardcoded valid params cannot fail») оказался неверным:
параметры действительно валидны, но вход — нет. Теперь `Assert\Regex('/\x00/', match: false)`
на всех трёх DTO и `str_contains($plainPassword, "\0")` в домене.

### D4. Логин не капаем — осознанно

Хеши, созданные до фикса из паролей длиннее 72 байт, верифицируются успешно:
`password_verify` усекает так же, как `password_hash`, то есть проверка
симметрична. Кап на логине превратил бы их вход в 422, а механизма сброса пароля
в проекте нет. Поэтому `LoginUserDTO` байтового лимита не имеет — только NUL-отказ
(иначе 500 воспроизводится на логине).

Это асимметрия контракта: создание ограничено 72 байтами, вход — нет. Она записана
в AssumptionLog как принятое ограничение, а не забытая.

### D5. Спека не врёт про единицы

`maxLength` в OpenAPI — кодовые точки, поэтому ставить там `72` было бы новой
ложью: 40 эмодзи (40 символов, 160 байт) выглядели бы допустимыми. `maxLength: 255`
остаётся, а на `register` и `admin/users` добавлено
`description: 'At most 72 bytes (UTF-8): bcrypt ignores the remainder.'`
На логине описания нет — там ограничения нет.

## Красные доказательства

Убран байтовый `Length` из `RegisterUserDTO` → регистрация 73-байтного пароля
перестаёт давать 422 (падает до доменного инварианта → 500) и 25 эмодзи тоже.
Два теста краснеют, после возврата — зелёные.

Отдельно важно: доменный кап даёт **громкий** 500, а не молчаливо ослабленный хеш.
Это сознательный выбор — тихое усечение и было дефектом.

## Приёмка

- [x] 73 байта → 422, 72 → 201, 25 эмодзи (100 байт) → 422;
- [x] NUL → 422 на регистрации и логине (было 500);
- [x] легаси-хеш из 100-символьного пароля: полный пароль → 200 **и** его 72-байтный префикс → 200 (подпись уязвимости, которую кап на логине закрыл бы ценой доступа);
- [x] спека: `description` на двух creation-путях, `maxLength` 255 везде;
- [x] `MultibyteLengthGuardTest`: аллоуанс `PasswordHash` 1 → 2 с причиной «оба — настоящие байты»;
- [x] `ci:all` 1147 тестов / 7505 ассертов.

## Что осталось

Минимальная сторона (8 в кодовых точках) не менялась: 2 эмодзи = 2 символа = 8
байт — отклонение корректно, дыры нет. Байтовый минимум, если понадобится, —
территория review-19 (там же multibyte-тема).
