# PRD 5.20 — замер длительности Code Review (форма A, утверждено)

Статус: done. Roadmap: `5.20`, `done`.

## Контекст

Исходная цель 5.20 («вернуть таймаут к ~10 мин») отменена замером 2026-09-27
(максимум 13.2 мин за 30 прогонов `Code Review`, ноль таймаутов). Рабочий объём
по строке Roadmap: «запись длительности прогона и пошаговых границ в step summary
+ фиксация находки; бюджет 35 и границы 12/15/2/3 остаются, `CodeReviewConfigTest`
не трогаем».

Замер 2026-09-27 (свежий, 30 прогонов, 2026-09-25…27): 28 success, 2 cancelled
(`cancel-in-progress` от нового пуша), 0 failure/timed_out. Run-level максимум
10.3 мин. Но `gh run list` меряет `createdAt→updatedAt`, т.е. **включая очередь
раннера**, а jobs-API (`started_at`/`completed_at` по шагам, `run_started_at` на
run) разделяет очередь и работу:

| Прогон | run | queue | job | primary | probe | fallback | detector |
|---|---|---|---|---|---|---|---|
| 36113981774 | 618 с | **575 с** | **36 с** | 27 с | <1 с | пропущен | 2 с |
| 36226107009 | 594 с | ~555 с | 39 с | 24 с | 6 с | пропущен | 1 с |
| 36260826829 | 559 с | 0 | **556 с** | 171 с | 12 с | **365 с** | 1 с |
| 36337721799 | 64 с | 0 | 64 с | 58 с | <1 с | пропущен | 1 с |

Примечание: run ≠ queue + job с точностью до секунд — оба числа берутся из jobs-API
и чуть по-разному оборачивают границы старта/конца; это не ошибка замера.

Выводы:
- «Долгий прогон» — это очередь GitHub-раннера (до 9.6 мин), а не ревью.
  Реальная работа: 36–64 с, primary 24–171 с, probe ≤12 с, detector ≤2 с.
- Единственный хвост работы — путь фолбэка (NVIDIA NIM, ~365 с на шаге, job 556 с).
- Худший наблюдаемый job 556 с против худшего пути 32 мин (1920 с) — запас ~3.4x.
- Записанное ранее число 13.2 мин было run-level (включало очередь) и снято с
  другого окна; свежий run-level максимум 10.3 мин. Посылка «ревью медленные»
  неверна дважды: run меряет очередь, LLM-путь занимает ~30 с.

## Решение (форма A, утверждено пользователем 2026-09-27)

Только фиксация + воспроизводимый скрипт. Причина: jobs-API уже отдаёт
пошаговые `started_at`/`completed_at` — маркеры в workflow дублировали бы его,
добавляя поверхность отказа в required-чеке. Отступление от буквы строки
Roadmap («в step summary») зафиксировано здесь: строка писалась до знания про API.

Не трогаем: `timeout-minutes` (35/12/15/2/3), условия фолбэка, `CodeReviewConfigTest`
(шаги ищет по имени, верхней границы на их число нет —
`tests/Infrastructure/Ci/CodeReviewConfigTest.php:94-98`; сумма бюджета читает
только четыре именованных таймаута).

## Декомпозиция

1. `scripts/review-timing-report.sh <run-id>` — печатает queue / job / пошаговую
   таблицу. Толерантен к отсутствию полей API (`n/a`, не падение). Проверка на
   трёх run id: с очередью (36113981774), с фолбэком (36260826829), без очереди
   и без фолбэка (36337721799). (0.25ч)
2. Одна строка комментария-доказательства в `.github/workflows/code-review.yml`
   рядом с «Worst path» (наблюдаемое за 30 прогонов). (0.05ч)
3. Доки: ARCHITECTURE.md (раздел CI/CD про Code Review — наблюдаемая структура
   затрат), AssumptionLog.md (замер + рецепт), Roadmap.md:148 → done. (0.1ч)
4. `composer ci:all` зелёный; `composer audit` чист; self-review; 3 ревьюера;
   amend; сквош; push; CI до зелёного; мерж за пользователем. (0.1ч)

Триггер повторного замера: первый `timed_out`/`failure` прогона Code Review —
прогнать скрипт на его run id и обновить таблицу и выводы выше (этот PRD —
канон; комментарий в workflow и строка в ARCHITECTURE указывают сюда и правок
не требуют).
