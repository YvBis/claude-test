# PRD: Task 4.3 — Сервис тегов (создание и переиспользование существующих)

## Описание задачи
Реализовать слой Application/Infrastructure для логики «найти-или-создать» тег: пользователь проставляет айтему имена тегов; для каждого имени сервер находит существующий тег (регистронезависимо) или создаёт новый. Задача даёт:
- `DoctrineTagRepository` (Infrastructure) — реализация `TagRepositoryInterface`, включая атомарный `getOrCreate(TagName)`.
- `TagService` (Application) — `resolveByNames(array $names)`, нормализация + дедуп + разрешение имён в `Tag`.
- Без миграций (схема `tags`/`item_tags` создана в 4.2).

Сервис **не флашит** — коммит остаётся за вызывающим (Task 4.4 `ItemService`), согласно выбранной стратегии (вариант B).

## Решения (согласованы с пользователем)
- **Вариант B — репозиторный атомарный upsert.** `getOrCreate(TagName): Tag` в Infrastructure: `findByName` → если нет, `INSERT ... ON DUPLICATE KEY UPDATE id = id` (MySQL) → повторный `findByName`. Гонка concurrent-создания разрешается БД (unique-lock), без исключений.
- **Doctrine остаётся в Infrastructure.** Application НЕ импортирует `Doctrine\DBAL\*`; `UniqueConstraintViolationException` не ловится в сервисе.
- **`UnitOfWorkInterface` не меняется.** `clear()` отклонён: сброс общего EntityManager отцепил бы pending-сущности вызывающего.
- **Flush у вызывающего.** `TagService::resolveByNames` не флашит; `getOrCreate` пишет строку тега атомарно и self-contained.
- **Вход — `array<string>` без DTO.** `TagName::fromString()` нормализует и валидирует (бросает `\InvalidArgumentException`).
- **In-batch дедуп.** Нормализация + дедуп по `value()` до записи; финальный дедуп по идентичности (`TagId`) после ci-разрешения.
- **Порядок сохраняется** — порядок первого появления.

**Отклонение от конвенции (зафиксировать в AssumptionLog):** конвенция проекта — `save()` отложен до `flush()`. `getOrCreate` пишет строку сразу, т.к. атомарность нужна немедленно, а ORM 3 не имеет partial flush (`flush($entity)` отсутствует) и auto-flush перед DQL (проверено: `AutoFlushMode`/`autoFlush` в `vendor/doctrine/orm` 3.6.7 отсутствуют).

## Ограничения
- MySQL-specific upsert (`ON DUPLICATE KEY UPDATE`) — допустимо: dev и test БД на MySQL.
- Слой Application: только `TagRepositoryInterface`, без Doctrine.
- `save()`/`remove()` интерфейса сохраняют конвенцию (persist/remove без flush).
- Class-level `#[ORM\UniqueConstraint]` уже на месте (4.2) — `uniq_tag_name`.

## Заметки (решения по ревью)

- **Семантика персистентности тегов.** `getOrCreate` пишет строку сразу. Если вызывающий (`ItemService`, 4.4) позже упадёт и откатит свою транзакцию, тег откатится вместе с ней (одна транзакция). Если вызывающий закоммитит, а создание айтема позже упадёт в отдельной транзакции — теги останутся. Это допустимо: теги глобальные и переиспользуемые, «осиротевший» тег безвреден. Подтверждено архитектурным ревью.
- **Пакетная оптимизация** `resolveByNames` (bulk-upsert вместо N round-trip) — вне scope; при >10 тегов на айтем завести отдельную задачу.
- **Raw SQL** привязан к именам таблицы/колонок `tags` — осознанная цена MySQL-specific атомарного upsert (dev/test на MySQL).
- **`wrapInTransaction` вокруг upsert отклонён**: единственный `INSERT ... ON DUPLICATE KEY UPDATE` уже атомарен, а вложенная транзакция DBAL без savepoints преждевременно закоммитила бы внешнюю транзакцию вызывающего.
- **`is_string`-гард для элементов `$names` отклонён**: контракт `array<string>`; валидация формы запроса — на уровне контроллера/DTO в 4.5.
