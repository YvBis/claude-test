# Задача 6.5 — Синхронизация коллекций с поиском

**Статус:** in progress (6.5b не закоммичен; в `done` — только по готовности PR)

## Цель

Замкнуть write-path: каждое создание, изменение и удаление коллекции доходит до индекса
`collections`, переименование рассылает новое имя по документам айтемов, удаление не
оставляет сирот несмотря на каскад в БД.

## Критерии приёмки

- [x] `CollectionService` пишет `indexCollection` после `flush()` на create/update
- [x] Rename детектится сравнением value-объектов до мутации; fan-out — `reindexCollection`
- [x] Delete собирает id айтемов скалярным чтением **до** `remove()`, затем `removeItem` + `removeCollection`
- [x] `ItemReindexer::reindexCollection` через общий `walk` с `reindexAll`
- [x] `CollectionReindexer` (параллельный класс, не обобщённый) + команда вызывает оба
- [x] Вывод команды `Indexed N item(s), M collection(s).`, engine-тест обновлён
- [x] `ci:all` зелёный, `coverage:gate` ≥ 80% (явный запуск)
- [x] `openapi.json` байт-в-байт
- [ ] Три ревьюера дали явный вердикт до коммита

## Решения

1. **Delete через скалярное чтение, а не постраничный обход.** Постраничный `findByCollectionId`
   с `clear()` между страницами отсоединяет саму коллекцию — `remove()` бросает
   `detachedEntityCannot`. Черновик плана содержал этот дефект, синьор поймал на ревью плана.
   `findIdsByCollectionId` — один скалярный DQL без пагинации и без очистки; правильный рид
   под настоящую нужду, не creep.
2. **Fan-out — метод на существующем `ItemReindexer`, а не инлайн и не новый сервис.**
   Paging + `clear()` + инвариант «документы до очистки» живут в одном классе через общий
   приватный `walk`; `CollectionService` владеет только детектом rename и порядком вызовов.
   Контроллер остаётся единственной точкой входа.
3. **Rename детектится сравнением VO до мутации.** `CollectionName` строится один раз из DTO,
   сравнивается с текущим через `equals`, затем переиспользуется в `changeName`. Пустая строка
   гаснет в `null` ещё в DTO и fan-out не триггерит; same-value rename не триггерит; case-only —
   триггерит (это настоящий rename).
4. **`indexCollection` — до fan-out.** Очистка внутри fan-out отсоединяет коллекцию, поэтому
   её документ должен уйти раньше.
5. **Bulk коллекций — параллельный класс.** Два почти одинаковых обхода дешевле обобщённого;
   у каждого свой тип документа и порядок. Флага `--entity` нет — нужды гонять один индекс
   не появилось; один `--batch-size` на оба обхода.
6. **Без try/catch в сервисе.** Fail-open — в адаптере (6.2); сервис падает громко при ошибке
   БД до записи в индекс.

## Триггеры пересмотра

- **Третий реиндексер — извлекать общий обходчик.** Два параллельных bulk-пути признаны
  дешевле обобщения; если появится третий (или один из двух получит prune, а второй нет) —
  выносить общий walk с fetch+build колбэками.

- Bulk-методы порта (`indexItems`/`removeItems` массивами): когда коллекция с тысячами айтемов
  начнёт заметно тормозить request path переименования/удаления (сейчас — по одному HTTP-вызову
  на документ, каждый в пределах таймаута 2с).
- Прунинг сирот коллекций — тот же триггер, что у айтемов (6.4): первая жалоба или расхождение
  счётчиков.

## Вне скоупа

- Маршруты, query-сторона — 6.6
- Прунинг документов удалённых строк — нет наблюдаемых потерь
