# Задача 6.4 — Синхронизация айтемов с поиском

**Статус:** in progress

## Цель

Сделать индекс живым: каждое создание, изменение и удаление айтема доходит до поиска, и
есть способ восстановить индекс целиком. Fail-open (6.2) без reindex-команды означает молча
протухший индекс без способа починки — поэтому команда входит в эту задачу, а не позже.

## Критерии приёмки

- [x] `SearchIndexerInterface` привязан к адаптеру в `config/services.yaml` (после ресурсного блока)
- [x] Имена индексов адаптера — из `MEILISEARCH_*_INDEX` с прод-дефолтами `items`/`collections`
- [x] `test.meilisearch_client` удалён; тесты берут клиент через тестовый контейнер
- [x] `ItemService::create/update` индексируют **после** возврата `transactional()`
- [x] `ItemService::delete` удаляет из индекса **после** `flush()`
- [x] Тесты: порт вызывается; rollback ⇒ не вызывается; flush упал ⇒ не вызывается; ретег ⇒ новые теги
- [x] `UnitOfWorkInterface::clear()` + реализация
- [x] `ItemRepositoryInterface::findAll(limit, offset)` со стабильным порядком
- [x] `ItemReindexer` в Application + команда `search:reindex`

## Решения

1. **Привязка — только в `config/services.yaml`, после блока `App\Infrastructure\`.** Прототип
   ресурса безусловно перезаписывает определение, загруженное раньше; в `meilisearch.yaml`
   аргументы адаптера молча терялись бы, адаптер получил бы дефолты `items`/`collections`, и
   тесты писали бы в продовые индексы. Изоляция 6.3 умерла бы без красного теста.
2. **Имена индексов через `%env(default:search.items_index:MEILISEARCH_ITEMS_INDEX)%`.** Голый
   `%env()%` бросил бы при инстанцировании в dev/prod, где переменной в `.env` нет; процессор
   `default:` падает на параметр с прод-именем. `%env()%` резолвится в рантайме, поэтому
   `symfony-diagnostics` (собирает, но не инстанцирует) не задет.
3. **Вызовы строго после коммита, без try/catch в сервисе.** `create/update` — после возврата
   `transactional()`; `delete` — после `flush()` (без окружающей транзакции DELETE
   автокоммитится). Если `flush()` бросит, `removeItem` не выполнится — индекс сохранит
   документ, что соответствует несостоявшемуся удалению. Fail-open остаётся в адаптере (6.2).
4. **`clear()` — в порт UoW, а не сырой EntityManager в команде.** EM в `src/` встречается только
   в `DoctrineUnitOfWork` и репозиториях; команда с EM нарушила бы эту дисциплину, а 6.5 нужен
   тот же шов.
5. **Reindex — Application-сервис + тонкая команда**, как у остальных use case. Свежая страница
   на каждой итерации + `clear()` после построения документов: переиспользование сущности после
   `clear()` дало бы detached-прокси к final-сущности.
6. **Дрейф offset-пагинации при конкурентных записях принят:** reindex идемпотентен, повторный
   прогон добирает пропущенное.

## Значения, взятые по умолчанию (владелец ответил «го» без ответа на вопросы)

- **HTTP-тесты бьют в настоящий адаптер — принято, не биндится тестовый no-op.** После
  привязки каждая мутация айтема через HTTP пишет в `items_test`. Fail-open гасит отсутствие
  движка, в CI движок есть, engine-тесты чистят индексы в setUp. Тестовый no-op скрыл бы ровно
  ту проводку, которую 6.4 добавляет. Пересмотреть, если появятся флаки от движка в HTTP-тестах.
- **Batch size 100 — догадка без данных об объёме.** Пересмотреть по замеру памяти/времени
  reindex на реальном объёме.

## Форма расширения для 6.5 (записано, чтобы 6.5 не переоткрывал)

- **Bulk коллекций** — параллельный `CollectionReindexer`, а не обобщённый `Reindexer<T>`;
  команда остаётся тонкой и вызывает оба после `ensureIndexes()` (флаг выбора — только если
  появится реальная потребность гонять один индекс). `ensureIndexes()` остаётся на адаптере:
  провижининг специфичен для движка; отдельный порт — когда появится второй движок.
- **Fan-out при переименовании коллекции — не reindex.** Это обновление `collection_name` у
  айтемов одной коллекции, отдельный путь (страницы `findByCollectionId` → `indexItem`), а не
  `ItemReindexer`, который обходит всю таблицу.

## Триггеры пересмотра

- **Offset → keyset-пагинация в `findAll`:** когда `search:reindex` перестанет укладываться в
  окно обслуживания (замер времени прогона), либо таблица айтемов превысит ~100k строк — offset
  на хвосте становится O(n) на страницу.
- **Прунинг документов-сирот:** reindex только upsert'ит; документ удалённого айтема остаётся,
  если движок был недоступен в момент удаления. Триггер — первая жалоба на «удалённое находится
  в поиске» или расхождение количества документов в индексе и строк в БД при сверке.
- **Внешняя транзакция вокруг `ItemService`:** запрещена (докблок сервиса) — внутренняя стала бы
  savepoint, индексация ушла бы до настоящего коммита.
