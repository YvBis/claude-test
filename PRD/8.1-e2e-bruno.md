# PRD — 8.1 E2E-тесты (Bruno)

**Статус:** done
**Задача Roadmap:** 8.1 — E2E-тесты: регистрация, вход, создание коллекции, создание айтема

## Цель

Проверить **собранный стек по HTTP** (nginx → php-fpm → MySQL/Redis/Meilisearch), а не ядро
внутри PHPUnit: сквозные пользовательские сценарии выполняются как внешний клиент и роняют
сборку при расхождении. Это тот пробел, который функциональные тесты не закрывают — они
ходят в ядро через `WebTestCase`, минуя nginx/php-fpm.

## Выбор инструмента

Исследованы 5 клиентов (Postman/Newman, Bruno, Apidog, Insomnia, HTTPie). Критерии:
headless-CI, коллекция в git, отсутствие обязательного аккаунта, ассерты и цепочки значений,
минимум нового тулчейна.

| Инструмент | Fit | Почему |
|---|---|---|
| **Bruno** | **5/5** | `.bru`-файлы plain-text в git, `bru run` с non-zero при падении, секреты через `--env-var`, офлайн по дизайну, core MIT |
| Postman | 3/5 | коллекция JSON 2.1 шумная; раскол авторство (v3 YAML)/раннер (v2.1); Free = 1 юзер |
| Insomnia | 3/5 | git-YAML, но метаданные пачкают диффы; exit-код при падении ассерта документирован тонко |
| Apidog | 2/5 | истина в облаке, обязательный аккаунт в CI — нарушает требования |
| HTTPie | 2/5 | нет раннера; цепочки/ассерты — самописный bash+jq |

Отвергнут `macarthy/bruno-mcp` (MCP-генератор `.bru`): 35 звёзд/3 коммита, только генерация
(не запуск), а `.bru` пишутся напрямую; MCP-клиент под такие серверы в проекте не заведён.

**Решение: Bruno** (`@usebruno/cli`). Отклонены: shell+curl (нет декларативных ассертов —
каждый статус/поле парсится руками), Postman (1-юзерный Free + раскол форматов).

## Сценарии (минимальный набор Roadmap + сквозной контекст)

Один прогон, порядок фиксирован `seq`; значения (token, id) прокидываются `bru.setVar`/`res`.

1. `POST /api/register` → 201 (в теле нет хеша пароля)
2. `POST /api/login` → 200; сохранить `token`, `userId`
3. `POST /api/collections` (auth) → 201; сохранить `collectionId`
4. `POST /api/collections/{id}/items` (auth) → 201; сохранить `itemId`
5. `GET /api/collections/{id}/items` (auth) → 200, айтем в списке
6. `GET /api/items` (auth) → 200 (свои)
7. `GET /api/items?owner={userId}` (auth) → 200
8. `GET /api/collections/{id}` **без токена** → 200 (гостевой read, fwd-7)
9. `POST /api/items/{id}/comments` (auth) → 201
10. `POST /api/items/{id}/likes` (auth) → 200
11. `GET /api/search/items?q=...` → 200 (движок жив)
12. `GET /api/admin/users` обычным юзером → 403 (авторизация держит)

Админовые роуты 200-пути (нужна роль) — вне скоупа 8.1: роль меняется SQL, а это не
пользовательский путь через API; покрыто функциональными тестами. См. «Вне скоупа».

## Контракт артефактов

- Коллекция: `tests/E2E/` (`bruno.json`, `*.bru`, `environments/{local,ci}.bru`), plain-text, диффабельна.
- `local`: `baseUrl=http://localhost:8000` (хост, docker compose). `ci`: `http://127.0.0.1:8000`.
- Секретов нет: пароль — тестовая константа; реальные секреты (JWT) — внутри стека.
- Запуск локально: `cd tests/E2E && bru run --env local` (Node 20+ на хосте; `bru` отказывается
  работать вне корня коллекции — потому и `cd`).
- Версия `@usebruno/cli` пинована (`4.2.1`) и локально, и в CI — `.bru` версионно-чувствительны.
- Выбор инструмента зафиксирован отдельно в `ADR/0002-e2e-client.md` (решение переживает задачу).

## CI

Новый blocking-job `e2e`: checkout → setup-ci → `docker compose up -d --build` → ждать
`/health` → миграции (`docker compose exec app`) → `setup-node` + `npm i -g @usebruno/cli` →
`bru run tests/E2E --env ci`. Стек поднимается через compose (реальный nginx/php-fpm), не
через `php -S`. Job добавляется в `needs:` у `ci-summary`.

## Вне скоупа

- Админовые 200-пути (роль через API не выдаётся пользователю — инвариант безопасности).
- Нагрузочное/браузерное тестирование (фронтенда нет).
- Smoke как отдельная задача — **8.2** (подмножество URL поверх того же job-инфра).

**Оговорки к приёмке:**
- CI-job `e2e` **не исполнялся локально** (нужен полный compose-стек на раннере); локально зелёная
  только коллекция. Проводка job проверяется первым прогоном CI на этом PR — его результат и есть
  доказательство.
- Сценарий поиска (11) — smoke: ассертит только 200 (движок жив), не содержимое. Содержательные
  проверки поиска — в функциональных тестах 6.6; синхронность индексации в E2E не гарантируем.
- Админовые 200-пути вне скоупа (роль через API не выдаётся — инвариант безопасности), покрыты
  функциональными тестами.
- **Пост-мерж фикс (готовность БД).** На прогоне main после мерджа миграции упали
  `SQLSTATE[HY000] [2002] Connection refused`. Корень: healthcheck БД пинговал сокет
  (`-h localhost`), а init-сервер MySQL на пустом volume отвечает по сокету до появления TCP,
  поэтому `depends_on: service_healthy` стартовал app раньше реальной готовности. Фикс: TCP-проба
  в `docker-compose.yml` (+ `start_period`) + шаг ожидания статуса здоровья `db` перед миграциями.
  Правка общая для локальной разработки: на уже поднятом контейнере `db` healthcheck может
  мигнуть при следующем `docker compose up` — либо дождаться реального init, либо
  `docker compose down -v`.
