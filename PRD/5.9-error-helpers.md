# PRD: Task 5.9 — Единые конверты ошибок в `AbstractApiController`

## Задача

Устранить размазанную обработку ошибок: каждый контроллер вручную собирал `JsonResponse` с конвертом `{error, message}` для 400/401/403/404/422, а `@var User` / `if (!$user instanceof User)` повторялся в каждом действии. Вынести построение конвертов и получение текущего пользователя в `AbstractApiController`, чтобы карта ошибок задавалась один раз.

**Источник:** Roadmap 5.9 (находка периодического review). Зависимость 5.10 (Voter) — выполнена.

## Что было (факты, замерено)

| Контроллер | Ручных конвертов | `instanceof User` guard'ов | `catch` |
|---|---|---|---|
| `CollectionController` | 16 | 5 | 10 |
| `ItemController` | 24 | 6 | 16 |
| `CommentController` | 21 | 6 | 7 |
| `LikeController` | 13 | 5 | 3 |
| `TagController` | 2 | 1 | 1 |
| `LoginController` + `RegistrationController` | 5 | 0 | 5 |
| **Итого** | **~81** | **23** | **42** |

Форм конверта — семь, включая две нестыковки: `['error' => 'Invalid owner id']` без `message` (`CollectionController`) и `{error, details}` от `createValidationErrorResponse` рядом с `{error, message}`.

## Решения

- **D1. Единый билдер + статусные хелперы** в `AbstractApiController`: `errorResponse(int $status, string $error, ?string $message = null, ?array $details = null)`, `unauthorized()`, `notFound()`, `forbidden()`, `badRequest()`, `unprocessable()`, `conflict()`, `internalError()`. `message` не добавляется в тело, если `null` — так сохраняется контракт 401/500 (только `error`).
- **D2. Guard на месте вызова, без обёртки над фреймворком:** `$user = $this->getUser();` + `if (!$user instanceof User) { return $this->unauthorized(); }`. Промежуточный хелпер `currentUserOrNull(): ?User` был написан и **убран по ревью PR #74**: `AbstractController::getUser()` уже возвращает `?UserInterface`, а сужение до доменного `User` всё равно делает `instanceof`-guard, так что обёртка дублировала фреймворк (форма `!$user instanceof User` — та, которую требует Rector `FlipTypeControlToUseExclusiveTypeRector`).
- **D3. Скоуп включает auth-контроллеры.** Roadmap называл 5 контроллеров, но `LoginController`/`RegistrationController` тоже содержали рукописные конверты (401/403/409) и уже частично использовали `createValidationErrorResponse`; без них «согласованность» осталась бы дырявой. Следствие — появился хелпер `conflict()`.
- **D4. Карта ошибок (правило, применяется ко всем контроллерам):**

  | Источник | Статус |
  |---|---|
  | id из пути не парсится / ресурс не найден | **404** |
  | нет токена | **401** (без `message`) |
  | не автор и не админ | **403** |
  | битый JSON / unserialize | **400** |
  | `limit`/`offset`/`query`/`owner` (query-параметры) | **400** |
  | DTO-валидация (`ValidationException`) | **422 + `details`** |
  | семантически невалидный контент (слот, пустой PATCH) | **422** |
  | непредвиденное (`\Throwable`) | **500** (без `message`) |

  Это **осознанное изменение контракта**: раньше DTO-валидация и невалидный контент отдавали 400 (кроме комментариев, где уже был 422), теперь — 422. Внешних клиентов у API нет (зафиксировано в fwd-18), поэтому унификация бесплатна сейчас и дорога после релиза. Разделение «400 — синтаксис/параметры, 422 — семантика» согласуется с формулировками, которые уже были в OpenAPI.
- **D5. Форма `details` сохранена** как отдельный контракт для списочных ошибок валидации: `createValidationErrorResponse()` остаётся, но внутри делегирует в `errorResponse(422, 'Validation failed', null, $details)`.
- **D6. Ревью-ассерты формы.** Тесты фиксировали статусы, но почти не фиксировали тела, поэтому добавлены проверки формы: 401 без `message`, 422 с `details`, `message` у 400/403/404/409/422, 401-конверт guard'а на публичном маршруте.
- **D7. Тело ошибки не пересказывает внутренние сообщения** (ревью PR #74, комментарии владельца). `message` стал стабильной обобщённой фразой, а конкретика причин ушла в `details` — для ошибок во входных данных клиента:
  - 404 → `'<Тип> not found'` без идентификатора (`Item not found`, `Collection not found`, `Comment not found`, `Like not found`) — было `Item with id "018f0a1b-…" not found`;
  - 400 (битый JSON) → `'Malformed request body'` — было сообщение serializer'а;
  - 400 (query-параметры) → `'Invalid query parameters'` + причина в `details` — было `limit must be between 1 and 100`;
  - 422 (контент) → `'Invalid content'` + причина в `details` — было `Comment content cannot be empty`;
  - 409 → `'User already exists'` без email — было `User with email "john@example.com" already exists`, то есть устранялся user-enumeration;
  - 403 → `'Forbidden'` вместо `You do not have permission to <действие>`; исключение — логин, где `'User account is deactivated'` объясняет отказ во входе в собственную учётку;
  - 500 → без `message` (как в D6); `details` DTO-валидации не меняется.

  Итого 56 конвертов и 6 примеров в OpenAPI. Текст исключения как диагностика для разработчика уходит в лог — задача fwd-21.

  Правило формулируется так: в `message` попадают **только стабильные фразы, написанные в коде проекта**; эхо `$exception->getMessage()` в `message` запрещено, а для клиентских ошибок ввода оно уходит в `details`. Отсюда два осознанных исключения, оставленных в `message`: `'User account is deactivated'` (логин — объясняет отказ во входе в собственную учётку) и `'At least one field must be provided for update'` (наша формулировка, не эхо). `details` — **best-effort диагностика**: её текст меняется вместе с сообщениями исключений (fwd-24). У 422 сосуществуют два лейбла — `'Validation failed'` (DTO-валидация, `details` = список сообщений полей) и `'Unprocessable Entity'` (семантика контента); сосуществование задокументировано и вынесено в fwd-22.

## Найденные и исправленные дефекты (не косметика)

1. **Битый JSON в `ItemController`/`CollectionController`/`LoginController`/`RegistrationController` → 500.** Эти контроллеры ловили только `ValidationException`, а `NotEncodableValueException` от serializer'а никто не обрабатывал; `CommentController` обрабатывал. Добавлен `catch (NotEncodableValueException|NotNormalizableValueException) → 400` (в `CommentController` это уже было — приведено к единому хелперу).
2. **Мусорный id в `PATCH`/`DELETE /api/collections/{id}` → 500.** В `update`/`delete` не было `catch (\InvalidArgumentException)`, хотя в `get` он был, а OpenAPI обещал 404. Добавлен `catch → 404`.
3. **`CollectionController`: `['error' => 'Invalid owner id']`** — единственный конверт без `message`; приведён к общему виду `{error: 'Bad Request', message: 'Invalid query parameters', details: ['Invalid owner id']}`.
4. **Дубль строки прогресса Этапа 5** в `Roadmap.md` (появился при правке предыдущей задачи) — удалён.

## Не входит в задачу (заведено как fwd-19)

401 на **защищённый** путь отклоняется `jwt`-entry-point'ом Lexik и отдаёт его тело `{"code":401,"message":"JWT Token not found"}`, тогда как guard контроллера на **публичном** пути (`GET /api/collections`, `PUBLIC_ACCESS` на firewall) отдаёт `{"error":"Unauthorized"}`. Единый 401-конверт требует кастомного entry point / failure handler — это изменение security-слоя, а не хелперов; заведено **fwd-19** (заодно поправить примеры 401 в OpenAPI, которые сейчас обещают `message`).

**Применено:**

- 🟡 Регрессионные тесты на исправленные `catch`-сайты (сходившееся замечание senior+architect): битый JSON в `Collection` create/update, `Login`, `Registration` → 400; мусорный id в `PATCH`/`DELETE /api/collections/{id}` и `PATCH`/`DELETE /api/items/{id}` → 404. Итого +8 тестов.

- 🔵 fwd-20: `CollectionController::list` парсит пагинацию сырым `(int)` — `?limit=abc` молча даёт `LIMIT 0`; заведено отдельной задачей (поведенческое изменение вне скоупа 5.9).

**Отклонено с причиной:**
- `errorResponse` сделать `private` (architect): метод — часть `protected`-поверхности базового класса (как `parsePagination`, `canManage`) и сознательно оставлен швом для контроллеров приложения и unit-теста; рекомендуемая поверхность — семь хелперов.
- Статичная подпись `'Malformed JSON body'` вместо `getMessage()` (senior): сообщение serializer'а эхом отдаётся и до 5.9 (`CommentController`), несёт диагностическую ценность для клиента с битым телом; утечки внутренних данных за пределами его же запроса нет. Формулировка в OpenAPI («malformed body») по-прежнему соответствует.
- «В Login-тестах нет проверки `details`» (tech-lead): проверка есть во всех трёх тестах (`assertArrayHasKey('details', …)`) — замечание основано на неполном чтении.
- Замена прокси-методов в `AbstractApiControllerTest` на атрибут/рефлексию (architect): прокси дают явный compile-time контракт сигнатур, а дублирование здесь осознанное — при изменении сигнатуры базового класса тест обязан обновиться.
- `createValidationErrorResponse` vs `errorResponse` (architect): принято «оставить оба», источник истины — `errorResponse`; шим сохраняет читаемость вызовов и документированный контракт `details`.

**Отложено (не блокирует):** миграция `canManage` на Voter; устранение per-action `if (!$user instanceof User)` через атрибут + listener (пересекается с fwd-17).
