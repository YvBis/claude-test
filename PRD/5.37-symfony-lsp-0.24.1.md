# PRD 5.37 — бамп symfony-lsp 0.23.0 → 0.24.1 и полный parity-зонд

Статус: выполнено (2026-10-21).
Roadmap: `5.37`, `done`.
Предшественники: `PRD/5.17-parity-probe.md` (исходный зонд), `PRD/5.26-symfony-lsp-version-bump.md`
(бамп 0.21.0 → 0.23.0, протокол которого повторяется здесь).

## Зачем

Задача заведена не по расписанию, а по сигналу: cron `dependency-drift` семь недель молчал
(в workflow не было `GH_TOKEN`, `gh` его сам не подхватывает, `|| true` глотал падение), и
после починки в `review-9` (#172) первый же ручной dispatch напечатал
`pin 0.23.0 lags the latest upstream release 0.24.1`. То есть дрейф был, но невидимый.

Бамп 0.x-бинарника — это два риска, а не один: (1) сама версия и её SHA256 (второй фактор
доверия beside TOFU-`SHA256SUMS`), (2) дрейф диагностик: 0.x не даёт гарантий semver, и
новая версия может как добавить коды, так и перестать ловить то, что ловила.

## Факты (измерено 2026-10-21)

- Upstream: `v0.24.1`, опубликован 2026-10-20T14:50:47Z; перед ним `v0.24.0` (2026-10-17).
- `symfony-lsp-v0.24.1-linux-x64.tar.gz` — `971bbc9fd051cc8eb2c5081651b10687e13fc8cc9c1f8999bb6a90e7800856c6`
  (digest asset'а с GitHub API совпадает с вычисленным при скачивании: `sha256sum -c` OK).
- Пин живёт в двух продюсерах: `.github/workflows/ci.yml` (`SYMFONY_LSP_VERSION`) и
  `scripts/symfony-lsp-check.sh` (дефолт `VERSION`). Третий «продюсер» — `pinned_sha256()`.
- Release notes 0.24.0/0.24.1 новых диагностических кодов не заявляют; правки — в сторону
  меньшего числа ложных срабатываний (YAML-дефиниции только из `config/`, декорированные
  Messenger-бусы, `extra.config-dir`, переиспользование неизменённых файлов индекса,
  Twig-компоненты и переводы).

## Методика зонда (повторяет 5.26, усилена по замечаниям ревью)

Все прогоны — **внутри контейнера** (`docker compose exec app`): на win32 `asset_name()`
выходит с кодом 11 для не-Linux/Darwin, а `var/` — анонимный том контейнера, поэтому
хостовая матрица физически невоспроизводима.

- Индекс (`var/symfony-lsp`) **не зависит от версии**, поэтому перед **каждым** прогоном:
  `rm -rf var/symfony-lsp var/cache/test` + проверка `test ! -e var/symfony-lsp`.
  `var/cache/test` важен отдельно: контейнер, скомпилированный с фикстурами, держит
  фантомные сервисы/маршруты.
- Бинарь и архив — в каталоге **на версию**: `SYMFONY_LSP_BIN_DIR=var/probe537/bin-<version>`,
  чтобы архив одной версии не переиспользовался другой.
- Команда: `bash scripts/symfony-lsp-check.sh --environment=test --format=json`; N=2, и
  второй прогон — **снова холодный**, а не «тёплый повтор».
- Фикстуры — временные, удалены до коммита: `templates/probe_537.html.twig` (P1/P6/P2),
  `config/services.yaml` (P3/P4), `config/packages/lexik_jwt_authentication.yaml` (P5).

### Набор кодов

`--list-codes`: **31** на 0.23.0 и **31** на 0.24.1, отсортированные множества совпадают

### Контракт гейта на 0.24.1

| Прогон | Отчёт | Гейт |
|---|---|---|
| Чистое дерево | `complete:true`, `runtime:ready`, diag 0 | exit 0, «complete report, 0 diagnostic(s)» |
| `--bridge-timeout=1` | `complete:false`, `runtime.state:failed`, error «project bridge timed out», exit 12 | **exit 1**, три `::error::`: «report is not complete», «project is not complete», «runtime.state is "failed", expected "ready"» |

Ключи схемы, на которые опирается гейт, на 0.24.1 на месте: `complete`,
`projects[].complete`, `projects[].runtime.state`, `summary.diagnostics`,
`summary.blocking`, `diagnostics[].severity/code/range/path`, `errors[].message`.
Замечание к формулировке: неполный индекс на **0.21.x** давал `runtime.state: stale`
(замер 5.14), а таймаут моста на 0.24.1 даёт `failed` — гейт проверяет «не `ready`»,
поэтому обе формы закрыты, и фикстура `gate-failed.json` фиксирует вторую форму.

### Найдено на CI: латентный баг раннера, не дрейф диагностик

Первый прогон на новой версии получил **холодный кэш** (ключ включает версию), и гейт упал с
`report unreadable (JsonException): Syntax error`. Причина: `sha256sum -c` печатает
`symfony-lsp-v0.24.1-linux-x64.tar.gz: OK` **в stdout**, а CI перенаправляет stdout скрипта
прямо в JSON-артефакт — проверка контрольной суммы писала в отчёт. На тёплом кэше этого не
видно, поэтому баг жил незамеченным с самого появления кэша: он воспроизводится на **любой**
смене ключа кэша, не только на бампе версии (5.26 прошёл зелёным именно из-за попадания в
кэш). Фикс: `sha256sum -c - >/dev/null` — ошибки остаются в stderr, своё сообщение о
несовпадении остаётся; инвариант закреплён гардом «проверка контрольной суммы не пишет в
stdout», потому что stdout здесь — канал данных.

## Решение

1. Пины: `ci.yml` → `'0.24.1'`, дефолт скрипта → `0.24.1`, шапка скрипта (`default:`) тоже.
2. `pinned_sha256()`: добавлена пара `0.24.1-linux-x64`, **пара 0.23.0 сохранена** — базовый
   прогон зонда остаётся two-factor, а не SHA256SUMS-only. Порядок в `case` семантически
   незначим; гард проверяет запись внутри блока `case "$1" in … *) return 1 ;;`, поэтому
   строка после catch-all не пройдёт.
   **Политика хранения:** держим пару текущей версии + предыдущей; при следующем бампе
   предыдущая удаляется, если её больше не требует ни один PRD. Строка без гарда — не
   риск: при явном override с несовпавшим хешем прогон падает громко, а не молча.
3. **Гард стал производным.** Прежний тест хардкодил версию и хеш в регексе, поэтому бамп
   `VERSION` без строки в `pinned_sha256()` проходил зелёным: `verify_pinned()` только
   предупреждает и возвращает 0, то есть второй фактор доверия деградировал молча. Теперь
   версия извлекается из того же якоря, что читает drift-скрипт, и тест требует
   `"<эта версия>-linux-x64") printf '%s' "<64 hex>"` в таблице. Красное доказательство:
   бамп `VERSION` без записи в таблице → тест красный.
4. Тексты, привязанные к версии: сообщения `SymfonyLspConfigTest`, докблоки
   `SymfonyLspGateTest` и `symfony-lsp-gate.php`, комментарии job'а в `ci.yml`,
   `ARCHITECTURE.md`.

## Риски и границы

- `workflow_dispatch` на ветке доказывает скрипт, якоря и `GH_TOKEN` **на этом дереве**, но
  не живость `schedule`: расписание исполняет workflow дефолтной ветки. Поэтому критерий
  приёмки раздвоен.
- P3 остаётся слепым пятном чекера при обеих версиях — это свойство инструмента, а не
  регрессия; границы: другие позиции (autowire-атрибуты, PHP type-hint) не тестировались.
- P5 как класс дефектов больше не воспроизводим: lexik 3.2 отвергает ключ до анализа.
- Первый прогон на `main` после мержа будет холодным (ключ кэша включает версию) — это
  ожидаемо и дороже обычного на один прогон.
