# PRD 5.14 — блокирующий флип symfony-diagnostics (PR-A: пин + флип + гард)

Статус: в работе. Roadmap: `5.14`, `todo`.

Пин SHA256 и флип — один PR: гейт, исполняющий бинарник, проверенный по списку
из того же релиза (TOFU), делает supply-chain блокирующим. Cron проверки
версии — отдельный PR-B. Слепые зоны `--environment=test` принимаем как
задокументированный риск; сверку Doctrine-схемы штатной командой выполнить
нельзя (ORM 3.7 требует DBAL ^4.5, стабильного нет — строки AssumptionLog
5.23/fwd-27); пробел прикрыт прогоном миграций на свежей test-БД + тестами.

## Гипотезы до замера

- **H1 (exit-код):** `symfony-lsp check` возвращает не-ноль при `blocking > 0`
  в обоих форматах (`json`, `github`). Если нет — носителем гейта становится
  конвертер, а не exit-код checker'а.
- **H2 (неполный индекс):** при неполном индексе отчёт несёт наблюдаемый
  признак (`complete: false` и/или `runtime.state != ready`). Если инструмент
  отдаёт `complete: true` при неполном индексе — гард на `complete` бесполезен,
  поля выбираются по факту замера.
- **H3 (TOFU):** `SHA256SUMS`, тянущийся из того же релиза, — единственное
  доверие; константа в репо закрывает его вторым фактором.
- **H4 (кэш):** `actions/cache` сохраняет `var/symfony-lsp` и при падении job'а;
  один неполный прогон делает все последующие тёплыми, то есть зелёными.

## Пробы (в контейнере, через bash — `$?` в PowerShell съедается)

1. Чисто: `--environment=test --format=json > f; echo exit=$?`
2. Один транзиентный boot-safe дефект (несуществующий шаблон из набора 5.17):
   тот же JSON плюс `exit=$?`
3. Тот же дефект в `--format=github` — различается ли поведение по форматам
4. Полный JSON на неполном индексе (снести `var/symfony-lsp`, оборвать
   построение) — до выбора полей гарда

## Результаты

Пробы в контейнере через bash (JSON вне репозитория):

| Случай | exit | `complete` | `runtime.state` | `blocking` | Диагностики |
|---|---|---|---|---|---|
| Чисто, json | 0 | true | ready | 0 | 0 |
| Дефект (`route.not_found`), json | 10 | true | ready | 1 | 1 |
| Тот же дефект, github-формат | 10 | — (аннотации) | — | — | 1 (`::error file=…,line=2,col=10,…`) |
| Обрыв секций (`--bridge-timeout=1`) | 12 | **false** | **stale** (`lastSuccessfulAt` + `Runtime indexing failed.`) | 0 | 0 |

Выводы:
- **H1 подтверждена:** exit-код несёт гейт (0/10) в обоих форматах.
- **H2 подтверждена с уточнением:** неполный индекс наблюдаем (`complete: false`,
  `runtime.state: stale`, exit 12). Но `blocking: 0` и пустой список при этом —
  гейт только по `blocking`/count был бы зелёным. Конвертер ассертит
  `complete === true` + `runtime.state === 'ready'` + `blocking === 0`.
- Координаты JSON 0-based (`lineBase: 0`), аннотации github 1-based (JSON
  line 1 → annotation line 2, col 9 → col 10): конвертер прибавляет 1.
- **H4 (кэш):** наблюдаемых тихих сценариев нет — все отказы громкие
  (exit 10/12, `complete: false`). `actions/cache` сохраняет кэш только при
  успешном job'е: «a new cache is automatically created provided the job
  completes successfully» (actions/cache README, раздел про restore+save) —
  красный job индекс не сохраняет; отдельный механизм защиты кэша не нужен.

## Решение

_По данным: поля гарда, форма конвертера, защита кэша._
