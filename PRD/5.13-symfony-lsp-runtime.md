# PRD 5.13 — `symfony-lsp` в CI: runtime-режим и надёжность скачивания

Этап 5 (Социальное), review-задача. Продолжение 5.11 (инфраструктура checker'а) и 5.12 (закрытие
единственной находки). Задача: перевести CI-job `symfony-diagnostics` с source-only на runtime-анализ
и убрать флейк скачивания релиза.

## Контекст и находки

1. **Корень флейка.** Job кэшировал `var/symfony-lsp` (индекс checker'а), а бинарник ставится в `var/bin`
   (`scripts/symfony-lsp-check.sh`) → кэш никогда не попадал → релиз (4.7 МБ) качался каждый прогон.
   При этом в скрипте не было ни `--retry`, ни таймаутов, поэтому одиночный транзиентный
   `curl: (22) ... error: 504` ронял job (наблюдалось дважды на PR #74).
   Кэширование бинарника было отклонено в 5.11 с формулировкой «восстановленный из кэша файл обошёл бы
   проверку SHA256». Формулировка неточная: инвариант — «хеш проверен **перед запуском**», а не
   «скачиваем каждый раз». Поэтому кэш возвращается **вместе с обязательной проверкой** архива.
2. **Окружение checker'а задаётся не `.env`.** Наблюдение: с `.env`, скопированным из `.env.test`
   (`APP_ENV=test`), и с полностью очищенным индексом checker всё равно сообщал `environment dev`.
   Смена процесса `APP_ENV` тоже не влияет. То есть по умолчанию он берёт `dev`, а в `dev`
   `cache.app` — `cache.adapter.redis` (`config/packages/framework.yaml`) → job'у потребовался бы
   Redis-сервис. Явный `--environment=test` (есть в `check --help`) решает это и совпадает с
   окружением, которое CI и так выбирает через `.env.test`.
3. **В test-окружении для boot не нужно ничего.** Проверено локально: очищенный `var/cache/test`,
   `--environment=test`, **недоступные** `DATABASE_URL` (127.0.0.1) и `REDIS_URL` (127.0.0.1) →
   `runtime metadata`, `complete`, `0 diagnostics`, `exit 0`. Значит ни MySQL, ни Redis-сервисы в job'е
   не нужны. APCu тоже не нужен: checker не инстанцирует `cache.app` (требование APCu относится к
   рантайму приложения — отдельно проверено: `cache:pool:clear cache.app --env=test` без расширения
   падает с «APCu is not enabled»).
4. **`--format=github` работает и в runtime-режиме** — проверено: в выводе появляется
   `::notice title=Symfony diagnostics::Project . analyzed with runtime metadata in the test environment.`

## Решения

- **Два прогона до parity-probe.** Source-only остаётся как baseline: не доказано, что runtime-анализ является
  надмножеством статического, а тихая потеря диагностик в non-blocking job'е недопустима. Это **не
  «навсегда»**: критерий выхода — задача 5.17 (parity-probe на фикстуре с заведомо статическими находками);
  при двух подряд зелёных прогонах source-only снимается из job'а и из скрипта. Без критерия выходы дублирующий
  прогон закрепился бы как вечная стоимость.
- **Кэш архива с ре-верификацией.** Кэшируются архив релиза и `SHA256SUMS.<версия>` в том же каталоге
  (`SYMFONY_LSP_BIN_DIR=var/symfony-lsp/bin`), на кэш-хите архив проверяется `sha256sum -c -` **до**
  распаковки. Бинарник **всегда** извлекается из архива, проверенного в этом прогоне: файл, восстановленный
  из кэша, никогда не проверялся (`SHA256SUMS` содержит хеши архивов, а не распакованного файла), а распаковка
  стоит миллисекунды. `SHA256SUMS` тянется заново; при недоступности GitHub используется закэшированная копия
  (тот же релиз, тот же уровень TOFU-доверия); список **по версии**, поэтому бамп не может сверить архив с
  чужим списком.
- **Надёжность скачивания.** `--retry 4 --retry-delay 2 --retry-all-errors --connect-timeout 10
  --max-time 60`: повторы лечат транзиентные 5xx, таймауты — зависший TLS-handshake (иначе он съедает
  весь бюджет job'а). Версия curl в runner'е (8.x) поддерживает `--retry-all-errors` (≥ 7.71).
- **Ключ кэша** включает версию checker'а и хеш `.symfony-lsp.json` (+ `composer.lock`), `restore-keys`
  без конфиг-хеша: статический ключ доказывал бы попадание, но не свежесть индекса.
- **Пилот не меняется.** `continue-on-error: true`, job не входит в `needs` у `ci-summary`; перевод в
  блокирующий — задача 5.14.
- **Таймаут 15 → 20 мин** (boot приложения + два прогона).

## Слепые зоны `--environment=test` (важно для флипа в 5.14)

Runtime-прогон идёт в **test**-окружении, потому что только оно поднимается без БД, кэша и транспорта.
Это значит, что будущий блокирующий гейт **не увидит**:

- `cache.app = cache.adapter.redis` (`config/packages/framework.yaml`) — в test он переопределён на APCu,
  то есть реальная Redis-обвязка prod/dev не анализируется;
- `when@test`-ветки конфигов и test-only бандлы (`dama_doctrine_test.yaml`, `framework.test: true`,
  mock-сессии) — контейнер анализируется в форме, которой в prod нет;
- сверку Doctrine-маппинга со **схемой** БД: соединения нет, метаданные читаются без подключения.

Прежде чем делать job блокирующим, 5.14 должна решить, нужен ли дополнительный прогон в `dev` с
Redis-сервисом (или `--no-cache`-прогон prod-формы) — иначе гейт окажется слабее, чем обещает название.

## Почему runtime, а не дешёвая проверка депрекейшенов

`lint:container` проверяет типы DI и физически не может поймать `config.deprecated_key` — то есть
единственный класс находок, который у нас реально был (5.12). Альтернатива — boot + разбор
Symfony-лога депрекейшенов — покрыла бы конфиг-депрекейшены, но job и так поднимает приложение,
поэтому полный checker добавляет к этому только время анализа и даёт маршруты, DI-контейнер,
Doctrine-метаданные и конфиги бандлов. Блокирующим job делает 5.14, там же — пиннинг digest'а
бинарника (сейчас `SHA256SUMS` тянется из того же релиза — TOFU).

## Критерии приёмки

- [x] Job выполняет **два** прогона checker'а, оба с `--environment=test`, и остаётся non-blocking.
- [x] Кэш покрывает и индекс, и архив; на кэш-хите архив проверяется по SHA256 до распаковки.
- [x] Скачивание имеет retry и таймауты; `SHA256SUMS` при недоступности берётся из кэша.
- [x] Guard-тест зелёный и фиксирует: два прогона, `--environment=test`, `continue-on-error`, версия,
      `SYMFONY_LSP_BIN_DIR`, независимость `ci-summary`, retry/таймауты в скрипте.
- [x] Локально: `composer ci:symfony-lsp` (runtime, dev) → `exit 0`, 0 diagnostics; прогон с
      `--environment=test` и недоступными БД/Redis → `exit 0`, 0 diagnostics.
- [x] `composer ci:all` зелёный; дифф не трогает `src/`.
- [x] В CI оба шага зелёные, кэш-архив переиспользуется (`using cached ... (checksum verified)`) — подтверждено run #35739005201
      (внешний блокер: аккаунт GitHub, run #35726467827). До этого задача числится `done` с пометкой
      «ожидает подтверждения в CI», а не как полностью проверенная.

- Git-политика для `config/reference.php` — fwd-11 (файл остаётся в `excludePaths`).
- Логирование пойманных исключений и глобальный `kernel.exception`-listener — fwd-21.

## Проверка вручную

```bash
docker compose exec app composer ci:symfony-lsp                        # runtime (dev)
docker compose exec app composer ci:symfony-lsp -- --source-only       # статический baseline
docker compose exec app composer ci:symfony-lsp -- --environment=test  # как в CI
```
