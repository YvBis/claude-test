## Исходная формулировка строки Roadmap

«Устранить потенциальный N+1 счётчиков в item-DTO при обогащении
`likes_count`/`comments_count`/`liked_by_me` (Этап 5, D6). **Если** агрегация на
каждый item списка даст N+1 — batch-подсчёт (`GROUP BY` по item_id для страницы) по
прецеденту fwd-6.»

Строка сформулирована условно, и условие ложно.

## Замер

Обогащение счётчиками происходит **только** в одиночном GET
(`ItemController::get:171-176` → `ItemDetailDTO::fromItem`). Оба списка
(`ItemController.php:80` и `:130`) отдают голый `ItemDTO` через
`ItemService::toDTOList` — счётчиков в списках нет вообще.

Все четыре вызова обогащения в контроллерах — на один айтем:

| Вызов | Где |
|-------|-----|
| `LikeService::countByItem` | `ItemController::get:173`, `LikeController:64` (возврат нового счёта после like/unlike) |
| `CommentService::countByItem` | `ItemController::get:174` |
| `LikeService::isLikedBy` | `ItemController::get:175` |

Одиночный GET стоит константу: `findById` (2 statement'а после fwd-6) + счёт
лайков + счёт комментов + `findByOwnerAndItem` — итого ~5 запросов на один айтем.
Это не N+1, это фиксированная цена детального просмотра.

Независимое подтверждение: в тестах списков (`ItemControllerTest:413`)
ассертится только `name`, а `likes_count` — только в тестах одиночного GET
(`:446`, `:468`, `:487`). Если бы списки обогащались, ассерты тел это бы
показали.

## Сохранённый дизайн батча (на будущее)

Сигнатуры спроектированы заранее (architect-ревью 5.3). Строить их сейчас —
мёртвый код: вызывать некому. Дизайн сохранён здесь, чтобы будущее обогащение
списков не проектировало заново:

- Репозиторий: `countByItemIds(array<ItemId>): array<string,int>` — `GROUP BY
  IDENTITY(...)` по item_id для страницы. Ключи карты — `toBytes()` (16-байтовая
  строка), не `toString()`: `IDENTITY()` для `binary`-FK возвращает сырые байты,
  и будущий вызывающий, который сверяет с `toString()`, молча промахнётся;
- Репозиторий: `likedItemIdsBy(OwnerId, array<ItemId>): array<string>` —
  `EXISTS`/`IN`. Возвращает список id через `toBytes()`; для страницы ≤100
  `in_array` приемлем, но если понадобится O(1) — ключуйте по той же строке.
- Сервис: `LikeService::countByItems(array<ItemId>)` / `likedItemIdsBy(...)`
  (аналогично Comment).

**Триггер**: появление счётчиков в ответе списка (продуктовое решение, не
перф-фикс — изменит форму ответа API).

## Вторая половина строки — `listByItem` и 4-join

«Перегидратация 4-join на список — кандидат на проекцию». Это не N+1, а широкий
запрос с константной ценой: `withAll()` тянет owner+item+collection+owner-за-
коллекцией одним запросом, DTO читают только заджойненное. Ленивых догрузок в
маппинге нет. Проекция схлопнула бы его, но убрала бы сущности из результата —
тот же трейд-офф, что в `fwd-6b`, и та же причина отложить: масштаб MVP, лимит
50. Отдельной строкой не заводим — `fwd-6b` уже покрывает «проекцию когда
вырастет», допишем туда полстроки про `listByItem`.
