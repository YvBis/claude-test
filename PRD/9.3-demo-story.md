# 9.3 — `DemoStory`: детерминированные демо-данные

Этап 9 (демо-данные для фронтенда), задача 9.3. Основание: `Roadmap.md` (этап 9),
`PRD/9.1-fixtures-stack.md` (стек Foundry), `PRD/9.2-factories.md` (шесть фабрик).

## Цель

Одна Story, которая наполняет тестовую/дев-базу набором, пригодным для разработки
фронтенда: фиксированные учётки для входа, все четыре темы, все двенадцать слотов,
теги, лайки и комментарии — и при этом воспроизводимым.

## Объёмы (точные константы, не «примерно»)

| Сущность | Кол-во |
|---|---|
| Пользователи | 50 (`admin@example.com` + `user01..user49@example.com`) |
| Коллекции | 200 (по 50 на тему: books/games/movies/drinks) |
| Айтемы | 1000 (~5 на коллекцию) |
| Теги | 40 (пул, аттач round-robin) |
| Лайки | 1500 (дедуплицированные пары owner+item) |
| Комментарии | 800 |

Все пользователи — пароль `password123`, хеш считается **один раз** за процесс
(`PasswordHash` мемоизирован, cost 13). `admin@example.com` — роль `admin`.

## Решения

### D1. `#[AsFixture]` не используется

Атрибут только вешает тег через autoconfiguration; сканирования классов в бандле нет
(`vendor/zenstruck/foundry/src/DependencyInjection/AsFixtureStoryCompilerPass.php`
потребляет теги, не создаёт их). Регистрация — явная, в `config/packages/fixtures.yaml`
под `when@dev`/`when@test` (неймспейс `App\Tests\` — autoload-dev, безусловная
регистрация уронила бы прод-контейнер). `autowire` + `autoconfigure` обязательны:
без первого не внедрятся зависимости конструктора, без второго не появится тег
`foundry.story` и `Story::load()` упадёт в `new $class()` → `ArgumentCountError`.

`DemoCatalog.php` исключён из ресурса — это данные, а не сервис.

### D2. Обещание детерминизма — узкое и проверяемое

Обещается: **контент, попадающий в отпечаток, воспроизводим в пределах одного метода
теста** при любом сиде faker. Не обещается: uuid7-идентификаторы, `createdAt`/`updatedAt`,
тексты комментариев и display-имена пользователей (faker), порядок строк в БД.

`FOUNDRY_FAKER_SEED` глобально не фиксируется (`phpunit.xml.dist` не меняется):
отпечаток от сида не зависит по построению, потому что строится только из литералов
каталога.

### D3. Отпечаток строится из БД, а не из каталога

Иначе он не может упасть: правка каталога меняла бы обе стороны сравнения. Каждая
запись сериализуется `json_encode(..., JSON_THROW_ON_ERROR)`, список записей
сортируется как строки (никогда по id), результат — sha256. Золотая константа лежит
в тесте и здесь.

| Запись | Поля |
|---|---|
| users | email, role, isActive |
| collections | name, theme, ownerEmail, descriptionIsNull, imageIsNull |
| items | collectionOwnerEmail, collectionName, itemName, 12 слотов, tags[] |
| likes | ownerEmail, collectionOwnerEmail, collectionName, itemName |
| comments | ownerEmail, collectionOwnerEmail, collectionName, itemName |

Детали, без которых отпечаток «плывёт»:
- embeddables проецируются точками: `u.email.email`, `u.role.role`, `c.name.value`, `c.theme.theme`;
- теги: LEFT JOIN по владеющей стороне (`Item::tags`), группировка по id айтема,
  `NULL`-строка (айтем без тегов) превращается в `[]`, имена сортируются
  `sort($names, SORT_STRING)` **после** маппинга — сортировка uuid7-id ничего не стабилизирует;
- даты — форматированной строкой, числа — фиксированной точностью (иначе
  `DateTimeImmutable` тащит таймзону, а float — хвосты представления);
- `json_encode` вместо разделителей: свободный текст слотов не имеет charset-валидации,
  и `|` внутри значения склеил бы разные раскладки в одну строку.

### D4. Единственный путь конвертации — `ItemSlotMapper`

Каталог хранит сырьё в форме `ItemSlotDTO` (`[type, slot, value]`). Story применяет
слоты через `ItemSlotMapper::applySlots()`, а не через `setSlotValue()` напрямую:
парсер дат живёт только в маппере (`asDate`, семь строгих форматов), и второй путь
конвертации означал бы второй набор правил. 9.4 использует тот же каталог через тот
же маппер.

### D5. Теги — пул, а не генерация на айтем

40 сущностей `Tag` создаются один раз (`TagName::fromString(...)` — VO, не строка:
Foundry не коэрсит, `Tag::__construct` ждёт `TagName`), затем аттачатся round-robin
по индексу айтема. `TagFactory` на каждый айтем дал бы >1000 имён вместо 40.
Литералы уникальны без учёта регистра (колонка `utf8mb4_0900_ai_ci`).

**Инвариант для 9.4:** множество имён пула = множество назначенных 1:1. Иначе
`TagService::resolveByNames` сминтит 41-й тег и отпечаток 9.4 разойдётся с 9.3.

### D6. Порядок записи и `flush`

`flush_once: true` флашит на каждый корневой `create()`. Наблюдение при реализации:
в текущем порядке (айтемы → слоты/теги → лайки → комментарии) последующие фабричные
создания всё равно флашат накопленные мутации, поэтому **удаление финального `flush()`
тест не краснит** — проверено отдельным прогоном. Значит вызов защитный, а не
несущий: он фиксирует последний хвост, не полагаясь на то, что после него случайно
окажется ещё одно создание. Оставлен осознанно; утверждение «без него слоты
потеряются» **неверно** и из плана убрано.

`clear()` внутри `build()` запрещён: сущности `final`, а `Like::$item`/`Comment::$item`
стали бы detached. Очистка — только в тесте после `load()`.

### D7. Создание батчами

Айтемы создаются `many()` по коллекциям, а не 1000 одиночных `createOne()`: каждый
`createOne()` — отдельный flush всего changeset.

## Инварианты, которые проверяет тест

1. Точные счётчики по шести сущностям.
2. Все четыре темы присутствуют.
3. Слоты: каждый айтем ≥1 заполненного; все двенадцать колонок >0; ≥1 айтем со всеми
   двенадцатью. Текст — `<> ''` (пустая строка не считается заполнением),
   остальные типы — `IS NOT NULL`. Матрица ожидания — в тесте, не в каталоге.
4. Каждый айтем принадлежит существующей коллекции; каждая коллекция — существующему владельцу.
5. `admin@example.com` существует с ролью `admin`; все 50 аккаунтов активны.
6. Уникальность имён: коллекции — в пределах владельца, айтемы — в пределах коллекции
   (схема этого не гарантирует; каталог гарантирует, тест держит).
7. Отпечаток совпадает с золотой константой.
8. Теги: ровно 40 сущностей; у каждого айтема 0–3 тега из пула.

## Красные доказательства (снимаются и откатываются)

| Поломка | Ожидание |
|---|---|
| убрать регистрацию `App\Tests\Story\` | `RuntimeException` на `Story::load()` (ArgumentCountError) |
| убрать финальный `flush()` | слоты/теги не в БД → красный инвариант слотов |
| заменить пул на `TagFactory` на айтем | тегов > 40 |
| изменить литерал каталога | отпечаток не совпадает |

## Границы

- Meilisearch Story не трогает: запись идёт через фабрики/EM, индекс обновляет 9.4.
- Прод-код не меняется: всё живёт в `tests/` и `config/packages/fixtures.yaml` под `when@`.
- Слоты `CollectionField` не используются — стек дормантный (см. `ARCHITECTURE.md`).

| Поломка | Наблюдение |

### Найденный по ходу дефект собственного плана

Генератор лайков «кандидат × 7 mod 50» и «кандидат × 37 mod 1000» имеет период 1000
пар: 1500 уникальных он не выдаст никогда, а rejection-loop крутился бесконечно
(первый прогон завис на 30 минут). Заменено на конструкцию без перебора: каждому
из 50 владельцев — 30 непересекающихся айтемов, 1500 пар уникальны по построению.
