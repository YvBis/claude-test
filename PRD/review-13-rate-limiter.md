# review-13 — rate limiting на login/register

Задача из review-бэклога (`Roadmap.md:251`). Обоснование в самой задаче: регистрация
создаёт аккаунт, логин крутит bcrypt-13, поэтому неограниченные попытки — это и подбор
пароля, и сжигание CPU (≈0.5–1 с CPU на попытку). JWT stateless, серверной сессии нет,
отзыв — только по TTL.

Три круга консультации (синьор NEEDS_FIX → принято, архитектор без блокеров,
техлид APPROVE). Ниже — решения и то, что ими отвергнуто.

## Решения

### D1. Три лимитера, а не один

| Лимитер | Политика | Лимит | Окно | Ключ |
|---|---|---|---|---|
| `login_account` | sliding_window | 5 | 15 мин | нормализованный email |
| `login_ip` | sliding_window | 20 | 1 мин | IP клиента |
| `register_ip` | sliding_window | 5 | 1 час | IP клиента |

Логин защищён по двум осям, потому что угрозы разные: подбор пароля ограничивается
по аккаунту (`5/15 мин` — порядка 500 попыток в сутки), сжигание CPU — по IP
(`20/мин` ≈ 20 CPU-секунд в минуту на источник). Регистрация — только по IP
(`5/час`): она не имеет «аккаунта-жертвы».

### D2. Слой — Infrastructure, компонент `AuthThrottle`

Изначально архитектор предлагал обойтись конфигом и двумя вызовами, синьор — общим
сервисом. Победил сервис: в вызове не одна строка, а нормализация ключа, fail-open и
расчёт `Retry-After`. Живёт в `App\Infrastructure\Security` рядом с `OwnerAccess` —
это транспортная защита, не бизнес-правило, и Application о ней знать не должен.

`RateLimiterFactory` инжектится по сервисному id `limiter.<name>` (проверено:
`FrameworkExtension.php:3524`), поэтому в коде нет строковых имён лимитеров.

### D3. Списание попытки — после валидации DTO

Синьор: иначе битый JSON или пустой пароль получает `429` вместо `422`. Ключ
`login_account` — email из валидированного DTO. Следствие принято осознанно:
поток мусорных запросов без валидного тела лимитом не ограничен, но он и не доходит
до bcrypt, то есть CPU не жжёт.

### D4. Ответ — исключение + ветка подписчика

`TooManyRequestsHttpException` бросается из `AuthThrottle`, конверт строит
`ApiExceptionSubscriber`. Это повторяет путь 403 («guard отказал»), а не путь
400/404 («вход не разобрался»).

**Почему ветка обязательна:** сегодня подписчик на `HttpExceptionInterface` молча
возвращает (`ApiExceptionSubscriber.php:63`), то есть брошенный 429 ушёл бы в
фреймворковый рендер без нашего конверта. Ветка ставится **перед** общим
`HttpExceptionInterface` и отдаёт `{error: 'Too Many Requests', message: ...}`
(контракт D10: `error` — reason phrase) плюс заголовок `Retry-After`.

`Retry-After` считается из `RateLimit::getRetryAfter(): DateTimeImmutable`
(`vendor/symfony/rate-limiter/RateLimit.php:48`), округляя вверх, минимум 1.

`details` машинным полем не расширяем: по D11 это человекочитаемый диагноз, а
машинный ответ даёт заголовок.

### D5. Fail-open

Redis недоступен → счётчик не списать; логируем `warning` и пропускаем запрос.
Причина: `RedisAdapter` соединяется жадно и на недоступном Redis бросит исключение,
то есть без обработки падение хранилища превратилось бы в падение логина (fail-closed).
Прецедент отношения к внешней зависимости — поиск (fail-open на записи). Принятое
ограничение: пока хранилище лежит, защиты от подбора нет. Записано в PRD и AssumptionLog.

### D6. Изоляция в тестах — array-пул, а не выключение

`cache.app` в test — APCu (процесс-глобальный), а ядро перезапускается на каждый
запрос: все логины сьюта попали бы в один бакет `127.0.0.1` и 429 прилетал бы в
случайные тесты, завися от порядка. Поэтому в `when@test` три лимитера получают
`cache_pool: cache.adapter.array`: состояние живёт в контейнере, обычные тесты его не
накапливают.

Выключить лимитер в test (предложение техлида) отвергнуто: тогда нечем доказать
реальный путь. Выделенный тест использует `disableReboot()`, чтобы счётчики
накапливались в одном контейнере.

### D7. Подделка IP — закрывается в nginx

Найдено при ревью и подтверждено кодом: `trusted_proxies: '127.0.0.1,REMOTE_ADDR'`
(`config/packages/framework.yaml:4`), а Symfony подставляет вместо `REMOTE_ADDR`
адрес каждого клиента (`vendor/symfony/http-foundation/Request.php:619-621`) — то есть
доверены все. nginx при этом `X-Forwarded-For` не выставлял, и клиентский заголовок
доходил нетронутым: IP-лимит обходился бы одной строкой.

Лечение: `fastcgi_param HTTP_X_FORWARDED_FOR $remote_addr;` — заголовок перезаписывается
реальным адресом соединения. Дополнительно guard-тест пинит директиву.

Принятое ограничение: за LB/CDN `$remote_addr` — это адрес балансировщика; для прода
понадобится `real_ip` (или доверие к конкретным подсетям). В этом стеке балансировщика
нет, поэтому вне скоупа.

### D8. OpenAPI

429 добавляется в оба экшена, спецификация регенерируется
(`composer openapi:generate`), пин-константа `RESPONSE_CODES` в
`OpenApiSpecTest` обновляется осознанно (она существует ровно для того, чтобы такие
изменения не проходили незамеченными).

## Отвергнуто

- **Автолимиты по имени маршрута** (`route`-key в конфиге) — спекулятивный механизм;
  два явных вызова читаются лучше, третий эндпоинт добавит три строки.
- **`X-RateLimit-*` заголовки** — не запрошены, контракт не расширяем.
- **Отдельный cache-пул для каждого лимитера** — меняет хранение, не семантику;
  общий `cache.rate_limiter` (→ `cache.app` → Redis) достаточен.
- **Circuit breaker вокруг лимитера** — лечил бы симптом; fail-open проще и честнее.

## Приёмка

- [ ] 6-я попытка логина в окне → `429`, конверт `{"error":"Too Many Requests",...}`, `Retry-After` ≥ 1;
- [ ] ключ аккаунта регистронезависим (`Admin@Example.com` и `admin@example.com` — один бакет);
- [ ] регистрация: 6-я попытка с одного IP → `429`, другие эндпоинты не затронуты;
- [ ] красные доказательства: убрать `consume()` → 429-тест красный; убрать ветку подписчика → конверт ломается;
- [ ] guard пинит `HTTP_X_FORWARDED_FOR $remote_addr` в nginx;
- [ ] `ci:all` зелёный, `openapi.json` регенерирован и свеж;
- [ ] Roadmap review-13 → done, AssumptionLog, ARCHITECTURE (карта ошибок + конфиг + fail-open + XFF).

## Оценка

3.5–4 ч: конфиг и компонент 1ч, подписчик и конверт 0.5ч, nginx+guard 0.5ч,
тесты и красные доказательства 1ч, OpenAPI и доки 0.5ч.
