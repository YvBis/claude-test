# PRD 5.17 — Parity-probe: runtime ⊇ source-only?

Этап 5 (Социальное), review-задача. Job `symfony-diagnostics` держал **два** прогона checker'а —
`--source-only` (статический baseline) и runtime — «навсегда», пока не доказано, что runtime-прогон
является надмножеством статического (architect-review 5.13). Guard-тест прямо требовал наличия
`--source-only` и ровно двух вызовов.

## Гипотеза и способ проверки

Справка checker'а 0.21.0: `--source-only` = «Disable runtime indexing and application execution».
`--list-codes` даёт **30 кодов**, и все до одного — разрешение ссылок (`config.*`, `service.not_found`,
`parameter.not_found`, `route.not_found`, `route.missing_parameters`, `template.not_found`,
`translation.*`, `twig_*`, `messenger.*`, `security.*`, `form.unknown_option`, `console.*`, `env.*` и т.д.).
Похоже, что без runtime-индекса статике нечего проверять — но это требовалось доказать замером.

Зонд: в ветке задачи транзиентно инжектированы дефекты, покрывающие разные классы (все boot-safe —
приложение поднимается, ошибки возникают только при выполнении затронутого кода), затем оба режима
прогнаны с `--format=json --environment=test` в контейнере.

| # | Дефект | Ожидаемый код |
|---|---|---|
| P1 | `#[Route('/api/probe/missing-param/{id}')]` без аргумента `{id}` в методе | `route.missing_parameters` |
| P2 | контроллер рендерит несуществующий `probe_missing_template.html.twig` | `template.not_found` |
| P3 | `abstract: true` сервис с аргументом `@app.probe_missing_service` | `service.not_found` |
| P4 | `abstract: true` сервис с аргументом `%app.probe_missing_parameter%` | `parameter.not_found` |
| P5 | возвращённый deprecated-ключ `lexik_jwt_authentication.encoder.crypto_engine` (задача 5.12) | `config.deprecated_key` |
| P6 | шаблон со ссылкой `path('app_probe_route_does_not_exist')` | `route.not_found` |

## Результаты

**Runtime-прогон (дважды; второй — с полностью удалённым индексом, N=2):** один и тот же набор из **4**
диагностик, `complete: true`, `blocking: 3`:
- `config.deprecated_key` — `config/packages/lexik_jwt_authentication.yaml` (P5)
- `parameter.not_found` — `config/services.yaml` (P4)
- `template.not_found` — `src/Infrastructure/Api/Controller/ParityProbeController.php` (P2)
- `route.not_found` — `templates/probe_route_reference.html.twig` (P6)

**Source-only прогон: 0 диагностик** — и на тёплом индексе, и после `rm -rf var/symfony-lsp`, с
`analysis.mode: source-only`, `runtime.state: disabled`, `source.state: ready`, `complete: true`. То есть
прогон исправен и пуст, а не сломан. Исправный отчёт, однако, сам по себе не доказывает, что статический
анализ не вырожден (молчаливое «всегда ноль» не исключено) — содержательная гарантия в другом: все 30
кодов, которые checker предлагает, разрешают ссылки по runtime-индексу, поэтому без индекса проверять
нечего.

**Не найдены ни одним режимом:** **P1** (`route.missing_parameters`) и **P3** (`service.not_found` на
абстрактном сервисе). Причина **не разведена**, и возможны два объяснения: (а) слепое пятно инструмента;
(б) артефакт фикстуры/ожидания — `route.missing_parameters` может относиться к месту генерации ссылки
(`path()`/`generate()`), а не к определению маршрута, а сервисы `abstract: true` компилятор удаляет (при
этом P4 той же формы сработал, что указывает на разницу в обработке service- и parameter-ссылок). Поэтому
«ограничение инструмента» здесь — гипотеза, а не измеренный факт. Целевая проверка P1/P3 — задача 5.26.

**Вывод (в границах замера):** на этом проекте и этой версии checker'а (0.21.x) source-only даёт пустое
множество, runtime — непустое, поэтому второй прогон не приносит ни одной находки, которой не было бы у
первого. Утверждение **не универсально**: оно измерено на одной фикстуре из шести классов дефектов и одной
версии инструмента; новая версия может добавить коды, для которых статический анализ что-то находит.
Поэтому снятие режима привязано к 0.21.x, а на бампе checker'а зонд повторяется (задача 5.26). Правило
«executable-code» не понадобилось: ни одной source-only-only находки нет.

**Расхождение с историей.** В дорожной карте 5.11 первая находка (`config.deprecated_key`) отнесена к
source-only пилоту. По этому замеру такой режим её не находит; вероятно, находка была получена
runtime-прогоном локально (в 5.12 она подтверждена именно runtime-режимом). Историю не переписываю,
но факт расхождения фиксирую.

## Решение

- **Снять `--source-only` из CI** (`.github/workflows/ci.yml`) — один runtime-шаг.
- Скрипт сохраняет возможность `--source-only` (для недоверенного кода), но в CI он не участвует;
  usage-комментарий обновлён.
- Guard-тест переписан: ровно **один** вызов скрипта, `--source-only` **отсутствует** (с объяснением и
  ссылкой на этот PRD), `--environment=test` закреплён, job остаётся non-blocking и не входит в
  `ci-summary`.
- **Контрольный прогон:** после снятия режима повторный зонд (тот же набор дефектов, только runtime)
  обязан поймать всё сам — и поймал: те же 4 диагностики в обоих прогонах.
- Инжектированные дефекты были **транзиентными**; в коммит ушли только `ci.yml`, guard-тест,
  usage-комментарий скрипта и доки.

## Критерии приёмки

- [x] Зонд покрывает route / template / service / parameter / bundle-config классы, все дефекты boot-safe.
- [x] Runtime-прогон дважды (N=2, второй — с холодным индексом) даёт один и тот же непустой набор.
- [x] Source-only прогон исправен (`complete: true`, mode `source-only`) и пуст — и на тёплом индексе, и на удалённом.
- [x] Ни одной находки, которую видит только source-only.
- [x] `ci.yml`: один runtime-шаг с `--environment=test`, комментарий объясняет снятие.
- [x] Guard-тест: один вызов, `--source-only` отсутствует, `--environment=test` закреплён, non-blocking, не в `ci-summary`.
- [x] README/ARCHITECTURE описывают режим CI = runtime.
- [x] `composer ci:all` зелёный.

## Не входит в задачу

- Поведение checker'а вне этого проекта (P1/P3 не диагностируются ни одним режимом; причина не разведена — слепое пятно инструмента или артефакт фикстуры, см. выше и задачу 5.26).
- Блокирующий флип job'а — задача 5.14 (после недели пилота; с одним прогоном он проще).
- Регулярная проверка версии checker'а и пиннинг SHA256 — задача 5.14.
