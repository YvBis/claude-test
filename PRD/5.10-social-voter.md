# PRD — Task 5.10: SocialContentVoter

## 1. Описание задачи

Модерация социального контента (`Like`/`Comment`) сейчас реализована императивно:
`AbstractApiController::canManage(User $user, User $owner)` (`src/Infrastructure/Api/Controller/AbstractApiController.php:95`)
вызывается в трёх местах:

| Контроллер | Метод | Строка |
|---|---|---|
| `LikeController` | `delete` | :198 |
| `CommentController` | `update` | :255 |
| `CommentController` | `delete` | :314 |

Метод дублирует бизнес-правило «автор или администратор» и не масштабируется: в
`ItemController` та же проверка применяется к владельцу коллекции
(`ItemController.php:279,361,427`), а в `CollectionController` — инлайн.

**Что создаём:** первый в проекте Symfony Voter — `SocialContentVoter` — принимающий
решение о модерации `Like`/`Comment`. Три перечисленных call-site переводятся на
`$this->isGranted(...)`. Ручной JSON-403 сохраняется (в проекте нет listener'а
`AccessDeniedException` → JSON).

## 3. Решения

| # | Решение |
|---|---|
| D1 | Только модерация `Like`/`Comment`. Доступ к айтемам/коллекциям остаётся на `canManage` (осознанный split-brain, унификация — 5.9/7.x). |
| D2 | `final class SocialContentVoter extends Voter` (не `VoterInterface` — deprecation-rules PHPStan). Путь: `src/Infrastructure/Security/Voter/`. |
| D3 | Константы `SOCIAL_EDIT`, `SOCIAL_DELETE`. |
| D4 | `supports()`: атрибут ∈ {EDIT, DELETE} **и** субъект `Comment`\|`Like` → true, иначе abstain. |
| D5 | `supportsAttribute()`/`supportsType()` переопределяются (фильтр по 2 атрибутам × 2 классам) — базовый `Voter` возвращает `true`, из-за чего voter вызывается на каждый `isGranted` приложения. |
| D6 | `voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool` + `#[\Override]` (3-й параметр — `TokenInterface`, `?Vote` в сигнатуре 7.4.14 отсутствует). |
| D7 | `Like` + `SOCIAL_EDIT` → **явный false до admin/owner** (реадактировать лайк нельзя, включая администратора). |
| D8 | `!$user instanceof User` → false (гость). |
| D9 | Админ — `$user->getRole()->isAdmin()` (доменная роль, не Symfony-строка `ROLE_ADMIN`). |
| D10 | Владелец — сравнение по значению: `getId()->toString() === $owner->getId()->toString()`. |
| D11 | `isGranted()` без `denyAccessUnlessGranted` — сохраняем ручной JSON-403 byte-identical и порядок 401→404→403. |
| D12 | `LikeController::deleteOwn`, `ItemController`, `CollectionController`, `security.yaml` не трогаем. `canManage` не удаляем. |
| D13 | Новых зависимостей и миграций нет. Регистрация — существующим `autoconfigure: true` (`config/services.yaml:33-36`). |

## 4. Ограничения

- Слои: Voter — Infrastructure (интеграция с framework), прямые ссылки на Domain-сущности допустимы (прецедент `UserProvider`).
- Doctrine ORM 3: read-путей не добавляется; `owner` уже гидрирован через `addSelect` (`DoctrineLikeRepository.php:96`, `DoctrineCommentRepository.php:109`).
- UoW/flush не затрагивается — Voter только читает.
- PHPStan level 6: явный `instanceof` перед `getOwner()`.
- Affirmative-стратегия (default `AccessDecisionManager`): DENIED одного voter'а **не veto** чужому GRANTED. Явный DENIED вместо abstain выбран, чтобы «Like+EDIT запрещено» было утверждением voter'а, а не следствием отсутствия grant'ов.
- Бюджет: Roadmap оценивал 2ч; по факту декомпозиции — **3ч** (ревизия зафиксирована здесь). Стоп-правило CLAUDE.md: при превышении 2x (4ч) — останов и передекомпозиция.

## 9. Заметки

- Гостевой кейс в unit-тестах — defense-in-depth: через API недостижим (`security.yaml` catch-all `^/api IS_AUTHENTICATED_FULLY`).
- Тестовая матрица обязана конструировать admin через доменный `Role::admin()`/`User::createAdmin()`, иначе voter увидит не-админа (он читает `getRole()`, а не Symfony-роли токена).
- `vote()` принимает атрибуты **массивом** — одиночная строка даст ложный abstain.
- Coverage gate измеряет только `src/Domain` + `src/Application`; Voter в Infrastructure **не попадает** в отчёт → его тест не «подразумевается», а обязателен.
- Кандидат на future: `SocialContentInterface { getOwner(): User }` в Domain вместо `instanceof`-веток.
- Кандидат на future: единый Voter для `ItemController`/`CollectionController` (сейчас `canManage`).
