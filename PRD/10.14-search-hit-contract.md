# 10.14 — Контракт поискового документа: битый индекс → 500

## Дефект

`ItemSearchHit::fromArray` (`:34-39`) и `CollectionSearchHit::fromArray` (`:28-32`) собирали хит через `(string) ($document['id'] ?? '')`. Документ без `id` или `name` превращался в валидный по схеме ответ с пустыми строками: клиент получал мусорные хиты вместо ошибки.

Это расходится с объявленной семантикой чтения. `SearchReaderInterface` докблок: «writes fail open and silent, reads cannot — a dead engine must surface as an error», а `MeilisearchSearchAdapter::buildFilter` прямо говорит «Deliberately no catch anywhere on this path». Битый документ был **тише** мёртвого движка: движок давал 500, документ — правдоподобный ответ.

**Почему поля обязательны — доказуемо.** Единственные писатели индексов — `ItemDocument::toArray()` и `CollectionDocument::toArray()`, и они всегда пишут все скалярные поля (`CollectionDocument:34` нормализует `null` description в `''`). Значит в индексе, который писали мы, отсутствующего поля быть не может: отсутствие или неверный тип — признак дрейфа схемы, ручной правки индекса или чужого reindex. Модель угрозы — out-of-band запись: сам движок primary key гарантирует, поэтому «документ без id» достижим только снаружи.

## Решение

**Смена поведения: fail-open → fail-closed на уровне формы документа.**

| Было | Стало |
|------|-------|
| отсутствующее поле → `''` | → `InvalidSearchDocumentException` → голый 500 |
| не строка (число, массив) → приведение к строке | → 500 |
| пустой `id`/`name`/… → `''` в ответе | → 500 |
| `tags`-скаляр → `['sci-fi']` | → 500 |
| `tags` отсутствуют / `[]` | → `[]` (смысл «нет тегов» сохраняется) |
| `description` пустая строка | → `''` (write-path сам нормализует `null`→`''`) |

Проверяются наличие, тип и непустота для `id`, `name`, `collection_id`, `collection_name`, `owner_id` (items) и `id`, `name`, `theme`, `owner_id` (collections). `description` — присутствие и тип `string`, пустота допустима. Значения не валидируются по смыслу (никакого enum темы, никакого UUID-разбора): это дублировало бы доменные VO в read-DTO.

**Исключение** — `App\Application\Search\InvalidSearchDocumentException extends \RuntimeException`. Модульное, рядом с хитами: бросает его сам модуль поиска, никто не ловит; Domain-исключения в проекте тоже живут по агрегатам. Общий `App\Application\Exception\` — для кросс-модульных трансляций (`ValidationException`, `ConflictException` 10.3b), здесь такой роли нет. База `\RuntimeException` обязательна: `SearchController` ловит только `InvalidArgumentException`, и «приведение к `InvalidArgumentException`» превратило бы 500 в 400 и утекло бы message в `details`.

**Правила полей** вынесены в `SearchDocumentFields` (`@internal`), чтобы оба хита не разъезжались: `nonEmptyString`, `string`, `tags`.

**Сообщение** называет класс хита и поле и не эхает содержимое документа (D11): `ItemSearchHit received a document without a valid "id" field`. Это же сообщение — единственная диагностика: фреймворк логирует необработанное исключение в канал `request` (`logKernelException`), свой лог в коде запрещён (5.32), клиент получает голый `{error: 'Internal Server Error'}`.

## Тесты

- `SearchHitContractTest` — юнит: round-trip валидных документов; отсутствие / пустота / неверный тип каждого обязательного поля → исключение с пиннутым сообщением; `description: ''` валидна; отсутствующие или `null` `tags` → `[]`; пустая строка в `tags` принимается (значения не валидируются, это вне скоупа); `tags`-скаляр и `tags` с не-строковым элементом → исключение.
- `MeilisearchSearchReaderTest` — адаптер: hit без `id` и hit без `name` проходят через реальный `Client`+`MockHttpClient` и бросают.
- `SearchContractFailureTest` — HTTP: подменяется **клиент** `Meilisearch\Client` (настоящий клиент поверх `MockHttpClient`), поэтому реальный адаптер и реальный `fromArray` обрабатывают частичный документ — стаб ридера обошёл бы валидацию через конструктор. `GET /api/search/items` и `/collections` отвечают 500 ровно `{error: 'Internal Server Error'}` без `message`; третий тест проверяет, что critical-запись в `monolog.logger.request` несёт наше исключение.
- **Красное доказательство:** возврат `?? ''` в один из хитов → юнит, адаптерный и 500-тест красные.

## Проверки

- `composer ci:all` — зелёный.
- Спека не регенерируется: схема успешного ответа не меняется, 500-конверт — общий контракт.
- `openapi:fresh` в `ci:all` подтверждает отсутствие дрейфа.

## Скоуп

Не входит: валидация смысла (`theme` как enum, UUID-формат id), изменение write-path, добавление 500 в OpenAPI сверх общего конверта, ретраи чтения. Acceptance Roadmap: документ без `id` → 500, обычный поиск зелёный — покрыт обоими уровнями.
