# PRD 5.28 — «Зелёный чек без вердикта»: фолбэк по публикации

Этап 5, review-задача (баг-строка Roadmap 5.28). Продолжение 5.19A: тот детектор сделал потерю
вердикта **видимой**, эта задача делает её **невозможной** — резервный провайдер запускается по факту
отсутствия вердикта, а не по коду выхода основного шага.

## Проблема

Экшен ревью может выйти с кодом 0, ничего не опубликовав. Тогда обязательный чек `OpenRabbit Review`
зелёный, вердикта нет, и branch protection (5.18) такой случай не ловит — она блокирует не-зелёный чек.

**Наблюдение (2026-09-24).** Из четырёх последних PR два (#84 и #87) получили зелёный чек без вердикта.
На #87 три автоматических прогона подряд (heads `146d266`, `057a926`, `f7860e0`) дали review с телом только
`Automated PR review generated by OpenRabbit.` — без строки `### Verdict`; четвёртая попытка (ручной
`gh run rerun` того же прогона) дала полноценный вердикт `ready to merge`. То есть провайдер флапает.

**Наш дефект, а не только чужой.** Условие фолбэка было `steps.openrouter.outcome == 'failure'` — по коду
выхода. Успешный no-op код выхода не меняет, поэтому резервный провайдер (NVIDIA NIM, свой ключ, своя
квота) не запускался **ни разу** за всю историю workflow. Дыра была не в провайдере, а в том, что мы
спрашивали «шаг упал?» вместо «вердикт есть?».

## Что показала разведка

**Лог прогона 35986972465 (успешного).** Экшен `aryanbrite/openrabbit@v0.8.7` — composite:
`actions/setup-node@v5` → `npm install` (80 пакетов, ~1.7 с) → `npm run build` (`tsc -p tsconfig.json`,
~1.6 с) → `node dist/action.js` (~84 с). **`dist/action.js` не печатает ничего** между
`##[start-action]` и `##[end-action]` — ни в успешном прогоне, ни в no-op.

Это опровергает формулировку, записанную ранее в `PRD/5.19a-verdict-publication-check.md` и
`AssumptionLog.md`: «экшен отчитывается об успехе, не напечатав ни строки вывода» звучало как признак
проглоченной ошибки. Молчание — **нормальное поведение** этого экшена; сигнал только один, и он снаружи:
что именно опубликовано. Формулировка исправлена здесь и в 5.19A.

**Тело-болванка — общий режим отказа.** `Automated PR review generated by OpenRabbit.` встречается на PR
в чужих репозиториях (в том числе в собственных PR openrabbit), то есть это поведение экшена, а не
следствие нашей конфигурации.

**Апстрим-фикса нет.** `v0.8.7` (2026-08-23) — последний релиз. Изменение «собрать `dist/` и убрать
`npm install` на каждый прогон» существует только как открытый PR в том репозитории, релизом не стало.

**Причина непрозрачна и недостижима.** Что именно теряется внутри экшена (пустой ответ free-пула
OpenRouter, суточный лимит 50 запросов, ошибка парсинга JSON-ответа модели) — из нашего репозитория не
видно: экшен не логирует. Чинить чужой код мы не можем; можем перестать терять вердикт.

## Решение

1. **Probe-шаг** `Check whether the primary provider published a verdict` (`id: primary_verdict`) после
   основного провайдера, `if: steps.openrouter.outcome == 'success'` — при упавшем основном публиковать
   было нечего, и probe только потратил бы ретраи. Запускает **тот же** скрипт в режиме `--probe`, который
   пишет в `$GITHUB_OUTPUT` трёхзначный результат `published|missing|unverified` и **не пишет
   комментариев**. Ретраи 3×5 с: список reviews eventually consistent сразу после публикации, но probe
   стоит между двумя вызовами провайдеров, поэтому его ожидание входит в бюджет job'а.
2. **Фолбэк по публикации:** `if: steps.openrouter.outcome == 'failure' || steps.primary_verdict.outputs.verdict != 'published'`.
   Сравнение **fail-open**: `missing` (не опубликовано), `unverified` (API нечитаем) и вообще не записанный
   output — все три дают запуск фолбэка. Это осознанное решение владельца: лишний вызов NVIDIA NIM дешевле
   потерянного вердикта.
3. **Один файл, а не два.** Режим `--probe` живёт в `scripts/verify-review-verdict.sh`, а не в отдельном
   скрипте: два определения «вердикта» — это ровно тот путь, по которому эвристика `### Verdict` со
   временем разъедется. Advisory-путь и его контракт не меняются.
4. **Output гарантирован на каждом пути.** `EXIT`-trap в probe-режиме дописывает `verdict=unverified`, если
   ничего не записано; `emit_verdict` пишет ровно один раз. Пустой output был бы тем же fail-open, но
   решение о фолбэке не должно зависеть от того, как именно умер скрипт, а не от того, что он нашёл.
5. **Финальный детектор 5.19A** остаётся без изменений и теперь срабатывает только тогда, когда вердикт не
   опубликовал **ни один** из двух провайдеров.
6. **Бюджет job'а считается целиком.** Guard-тест раньше пиннил только `primary + fallback < 30`; теперь
   пиннит `primary + probe + fallback + detector < 30` (12 + 3×5с + 15 + 5×10с = 28.08 < 30), и оба
   check-шага задают свои ретраи явно в `env`, чтобы арифметика не разъехалась с workflow.

## Решения владельца (2026-09-24)

- **Частота фолбэка.** Привязка к публикации означает запуск NVIDIA NIM примерно на 75% PR (наблюдаемая
  доля no-op — 3 из 4). Принято: NIM-квота дешевле потерянного вердикта, free-пул OpenRouter на ретрай не
  тратится.
- **`unverified` → фолбэк запускать** (fail-open), а не только предупреждать.
- **Два review бота на одном head — оставляем.** Если основной опубликовал болванку, а NIM затем вердикт, в
  PR будет два review. Детектор считает PR опубликованным по одному телу со строкой `### Verdict`;
  болванка основного не удаляется и не перезаписывается.
- **Ретраи финального детектора 5×10 с пока остаются.** Худший путь (основной 12 мин + фолбэк 15 мин +
  check-шаги) укладывается в 30 мин с запасом ~2 мин, но при исчерпании бюджета job убивается и `always()`
  -детектор не стартует — предупреждение теряется ровно там, где оно нужнее всего. Принято осознанно,
  вынесено в 5.29.
- **Один скрипт** вместо отдельного probe-скрипта (см. п.3).

## Проверка

**Зонд probe-режима (19 проверок, все зелёные; временный зонд не коммитится):**

| Сценарий | Ожидание | Результат |
|---|---|---|
| живой API, реальный вердикт (head PR #86) | `published`, без комментариев, exit 0 | `published`, лог вызовов пуст |
| стаб: review не опубликован | `missing`, без комментариев | `missing`, лог пуст |
| живой API, неизвестный SHA на PR #86 | `missing` | `missing` |
| стаб: API отвечает ошибкой | `unverified`, exit 0 | `unverified`, лог пуст |
| отсутствуют аргументы | `unverified`, exit 0 | `unverified` (trap) |
| `GITHUB_OUTPUT` не задан | не падать, результат в stdout | exit 0, `missing` в выводе |
| advisory-режим: вердикт есть | комментариев нет, exit 0 | лог пуст |
| advisory-режим: вердикта нет | `POST`, exit 0 | `POST` |
| advisory-режим: нет аргументов | exit 0 | exit 0 (trap) |
| `bash -n` | чисто | чисто |

**Guard-тест (7 тестов, 75 ассертов) и негативные пробы** — правка workflow транзиентно ломалась и
восстанавливалась байт-в-байт, каждая поломка валила guard по нужной причине: откат условия фолбэка к
`outcome == 'failure'`; потеря `--probe` в probe-шаге; `VERDICT_ATTEMPTS: '9'` + `VERDICT_DELAY: '30'`
(бюджет 31.75 > 30).

## Риски

**Probe без `continue-on-error`.** У шага нет страховки на уровне workflow: если скрипт выйдет ненулевым
**до** установки trap, упадёт обязательный чек и мержи встанут. Единственный реальный путь к этому —
синтаксическая ошибка (bash отказывается запускать файл, trap не выполняется), поэтому guard-тест гоняет
`bash -n`. Все остальные пути (нет аргументов, `gh` недоступен, ошибка API) проходят через trap и дают
`unverified` + `exit 0`. Роллбэк — откат коммита.

**Fork-PR.** Секретов нет: основной экшен либо падает, либо выходит 0 без публикации. Тогда probe даёт
`missing`/`unverified`, фолбэк запускается и падает (нет `NVIDIA_API_KEY`) → job красный → мерж
блокируется. До 5.28 такой PR мог получить зелёный чек с предупреждением. Для этого репозитория (один
владелец, форков нет) поведение принято; при появлении внешних вкладов решать отдельно — например,
пропускать review-job для fork (`if: github.event.pull_request.head.repo.full_name == github.repository`).

**Оба провайдера — один и тот же экшен.** Если молчаливый no-op окажется свойством экшена, а не модели,
фолбэк его унаследует: спасает другой провайдер и ключ, а не другой код. Альтернатива (свой вызов NIM
через `curl` вместо экшена) в этой задаче не рассматривалась и в бэклог не вынесена — если NIM тоже начнёт
no-op, это первое, что стоит проверить.

## Не входит в задачу

- **Починка самого экшена** (почему `dist/action.js` молча ничего не публикует). Апстрим-фикса нет,
  логов экшен не даёт; эта задача делает потерю вердикта невоспроизводимой, а не устраняет её причину.
- **Пересмотр бюджета худшего пути** — 5.29.
- **Детекция `cancelled`/`timed_out` и триггер `reopened`** — 5.19B. Разведка 2026-09-24 уточнила её
  постановку: `cancelled`/`timed_out` **и так** блокируют мерж (успешные conclusions — только `success`,
  `skipped`, `neutral`), устаревший отменённый прогон перекрывается более новым по тому же имени чека, а
  workflow на `workflow_run` **не может** быть required-чеком (его событие не входит в список оцениваемых).
  Поэтому B — только диагностический комментарий, а C не разблокирует мерж: `reopened` не меняет head SHA,
  и старый зелёный чек остаётся валидным. Строка 5.19B обновлена этой поправкой. **2026-09-25:** 5.19B
  закрыта как устаревшая полностью (разведка live: все 8 `cancelled` из 100 прогонов superseded, терминальных
  отмен 0, `timed_out` 0) — детектор не строится, триггер `reopened` не добавляется.
