# Задача 6.2 — Модель документов и порт индексации

**Статус:** in progress

## Цель

Дать поиску шов в Application и реализацию в Infrastructure: документы двух индексов,
порт записи, адаптер Meilisearch с fail-open и настройки индексов как данные. Индексация
в доменных сервисах **не** вызывается — это 6.4/6.5; здесь только callee и его контракт.

## Критерии приёмки

- [x] `SearchIndexerInterface` в `Application\Search` — `indexItem`/`removeItem`/`indexCollection`/`removeCollection`
- [x] `ItemDocument::fromEntity` — `id`, `name`, `tags` строками, `collection_id`, `collection_name`, `owner_id`; без слотов
- [x] `CollectionDocument::fromEntity` — `id`, `name`, `theme`, `description` (null → `''`), `owner_id`
- [x] `IndexSettings` как данные: searchable/filterable для обоих индексов
- [x] `MeilisearchSearchAdapter` реализует порт; конструктор не делает HTTP; fail-open с логом, без rethrow
- [x] `ensureIndexes()` вне порта, толерантен к повторному созданию (через ожидание задачи, см. ниже)
- [x] Тесты документов (все поля, пустые теги → `[]`)
- [x] Тесты адаптера с `MockHttpClient`: успех (URL + payload), 500 молча, обрыв молча, настройки совпадают
- [x] `ci:all` зелёный
- [x] `coverage:gate` ≥ 80% (явный запуск — `ci:all` его не содержит): 97.96%
- [x] `openapi.json` байт-в-байт не изменился
- [x] Три ревьюера дали явный вердикт до коммита: senior NEEDS-CHANGES, архитектор SHIP-WITH-NITS,
      техлид NEEDS-CHANGES; замечания внесены (асинхронный `index_already_exists`, дрейф Roadmap,
      запись в AssumptionLog, отложенное снятие алиаса)

## Решения (записываются, не реализуются)

1. **`owner_id` входит в документ айтема.** Он immutable — у `Collection` нет `changeOwner` —
   поэтому reindex не триггерит. Без него фильтр «свои» в 6.6 невозможен: Meilisearch не
   фильтрует атрибут, которого нет в документе.
2. **Слоты в документ не входят.** Ни одно требование не ищет и не фильтрует слоты
   (`artifacts/prd-taskflow-ru.md:27,38,54`: поиск — имя, теги, имя коллекции). Отложено с
   указанием требования, которое вернёт их обратно.
3. **`collection_name` денормализовано в документ айтема.** Это и есть причина, по которой
   переименование коллекции требует bulk-reindex её айтемов (6.5): поиск без join против
   стоимости переиндексации. Решение записано здесь и указано в ADR.
4. **Видимость поиска — публичная**, с опциональными фильтрами «свои»/«эта коллекция».
   Не owner-or-admin: `security.yaml` уже даёт `^/api/search` `PUBLIC_ACCESS`, fwd-7 открыл
   чтение. `owner_id` filterable только потому, что 6.6 предлагает «свои».
5. **`addDocuments`/`deleteDocument` — постановка задачи в очередь, не синхронная запись.**
   ADR говорит «синхронная» в смысле «из PHP-процесса, без брокера», а не «ждём завершения».
   `waitForTask` не нужен: порядок delete/re-add сериализует движок. Записано, чтобы никто не
   «оптимизировал» latency ожиданием в пути запроса.
6. **Fail-open — свойство адаптера, не порта.** Порт описывает намерение; проглатывание —
   свойство конкретной реализации.
7. **Call sites — 6.4/6.5, не здесь.** Универсального post-commit шва нет: `ItemService::create`/
   `update` обёрнуты в `transactional()`, у `delete` и всего `CollectionService` транзакции нет
   (save/remove + `flush()`). Вызывающий владеет местом вызова; 6.2 определяет только callee.
   Докблок порта документирует этот контракт.

## Вне скоупа

- Вызов порта из `ItemService`/`CollectionService` — 6.4/6.5
- Реальный движок в CI, health-check, провижининг — 6.3
- Маршруты, OpenAPI, scoping в запросах — 6.6
- Bulk-reindex, fan-out переименования/удаления коллекции — 6.5

## Открытые вопросы

- Честная граница Red/Green: мок-тесты 6.2 — это каркас контракта, **не** доказательство, что
  v1.54 принимает payload'ы и настройки. Проверка против реального движка — 6.3. Записано,
  чтобы Red/Green не был переоценён.
- `ensureIndexes()` вызывается в 6.3 (провижининг в CI). В 6.2 он существует и покрыт тестом,
  но не вызывается рантаймом.
- **6.4 обязан завести алиас `SearchIndexerInterface` → `MeilisearchSearchAdapter`**: без него
  автосвязывание порта не разрешится, конструктор не примет интерфейс. Сам адаптер
  регистрируется автоматически (`config/services.yaml`), но он приватный и до 6.4 вырезается.
- **`index_already_exists` — асинхронная ошибка задачи, не синхронный HTTP-ответ.** Измерено
  против v1.54.3: повторный `POST /indexes` отвечает **202** и ставит задачу `indexCreation`,
  которая затем падает с этим кодом. Первая редакция ловила `ApiException` с проверкой
  `errorCode` — этот путь недостижим, и толерантность была мёртвым кодом, а тест проверял
  выдуманную форму (HTTP 400). Исправлено: `createIndex` ожидается через `waitForTask()`,
  толерантность проверяет `status === 'failed'` и `error.code`. Ожидание заодно снимает гонку
  между созданием индекса и последующим PATCH настроек.
