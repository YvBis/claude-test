# PRD 5.19A — «Зелёный job без вердикта»

Этап 5, review-задача. Из senior-review 5.16 в бэклог вынесены два пункта: (а) словарь исходов
`steps.<id>.outcome` не зафиксирован, (б) «вердикт опубликован» ≠ «job зелёный». Задача 5.19 разбита на
три части: **A** (этот PRD) закрывает (б), **B** — механическую детекцию `cancelled`/`timed_out`, **C** —
триггер `reopened`.

## Проблема

Экшен ревью может выйти с кодом 0, ничего не опубликовав, и тогда обязательный чек `OpenRabbit Review`
становится **зелёным без вердикта**. Branch protection (5.18) такой случай не ловит: она блокирует
не-зелёный чек, а здесь чек зелёный.

**Наблюдение, а не гипотеза.** На PR #84 бот оставил ровно один review со `state=COMMENTED` и телом
`Automated PR review generated by OpenRabbit.` — без строки вердикта, при полностью зелёном job'е. На
PR #85 и #86 тот же экшен в том же workflow дал тело, начинающееся с `### Verdict`. То есть формат
дрейфует, и отличить «одобрено» от «ничего не опубликовано» по цвету чека нельзя.

Второй источник того же класса — fork-PR: секреты недоступны, экшен завершается, вердикта нет.

## Почему детектор advisory, а не гейт

Соблазн — падать (`exit 1`), но это создаёт **вечную блокировку**: `### Verdict` не является
контрактом с `aryanbrite/openrabbit@v0.8.7`, а required-чек, упавший на дрейфе формулировки
третьей стороны, не позеленеет никогда и не даст смержить ни один PR. Поэтому:

- детектор **всегда выходит с кодом 0**;
- отсутствие вердикта фиксируется **sticky-комментарием** в PR + `::warning::`-аннотацией (видна в
  checks UI) + строкой в step summary;
- сигнал «нельзя мержить» остаётся там, где он уже есть механически — в required-чеке 5.18.

## Почему детекция `cancelled` — не в этом PR

Шаг внутри job'а **не может** увидеть отмену или убийство по `timeout-minutes` своего же job'а:
последующие шаги просто не выполняются. Это свойство runner'а, а не недоработка формулировки, поэтому
задача переформулирована: детекция отмены возможна только снаружи, через событие `workflow_run`
(часть **B**). Здесь закрывается ровно то, что достижимо изнутри job'а.

## Решение

1. **Новый финальный шаг** `Verify a verdict was published for this head` в job'е `review`:
   `if: always()` — обязан выполняться и после падения фолбэка (у него нет `continue-on-error`, job
   падает, но `always()` шаг всё равно идёт); **без** `continue-on-error` — детектор нельзя тихо
   отключить, а его advisory-контракт обеспечивает сам скрипт.
2. **Логика — в `scripts/verify-review-verdict.sh`** (по образцу `scripts/symfony-lsp-check.sh`):
   вердикт считается опубликованным ⟺ есть review, у которого `user.login == github-actions[bot]`,
   `commit_id == head SHA` **и в теле есть строка `### Verdict`**. Строго по SHA: вердикт на устаревшем
   коммите ничего не говорит о том, что мержится. Пустой `commit_id` не принимается — это источник
   ложных срабатываний. Проверка строки — **эвристика, а не контракт**, поэтому её провал даёт advisory,
   а не падение. Предупреждение различает два диагноза: «review опубликован, но без строки вердикта» и
   «review не опубликован вовсе» — второе сообщение стоило бы отдельного расследования, а не общего текста.
3. **Retry 5×10 с** (`VERDICT_ATTEMPTS`/`VERDICT_DELAY`, с валидацией: нечисловое значение
   откатывается к дефолту): список reviews в API eventually consistent, одиночное чтение давало бы
   ложное «нет вердикта» слишком часто.
4. **Sticky-комментарий с маркером** `<!-- opencode-verdict-missing <sha> -->`: перед POST ищем
   существующий комментарий **того же автора** с этим маркером и делаем PATCH. SHA в маркере не даёт
   переписать предупреждение о старом коммите в утверждение о текущем, а фильтр по автору не даёт
   затереть чужой комментарий, случайно содержащий маркер. Для части **B** зарезервирован отдельный
   префикс `opencode-verdict-cancelled`, чтобы два детектора не сталкивались.
5. **Отдельная ветка «не смог прочитать»**: если API недоступен все попытки, пишем «вердикт не
   проверен», **не** публикуя обвинение в отсутствии вердикта, — недоступность API и отсутствие
   вердикта это разные находки.
6. **Advisory-гарантия на уровне скрипта**: `EXIT`-trap превращает любой ненулевой статус (включая
   неожиданный внутренний сбой под `set -e`) в `::warning::` и выходит 0. Без этого шаг без
   `continue-on-error` ронял бы обязательный чек, то есть внутренняя ошибка скрипта блокировала бы мержи.
7. **Снятие предупреждения при появлении вердикта**: если вердикт найден, а предупреждение по этому
   head уже стоит, скрипт удаляет свои предупреждения. Иначе сигнал противоречил бы сам себе: текст
   предупреждения советует перезапустить ревью, а после перезапуска старая отметка осталась бы висеть.
   Отказ в удалении репортится, но шаг не роняет.
8. **Словарь исходов** — документацией: комментарий в workflow + этот PRD.

## Живая проба на PR #87 (сам PR и есть проба)

Отдельная ценность этой задачи: она проверяется собственным прогоном. Результаты первого же прогона:

- **Права подтверждены эмпирически:** `POST /repos/{owner}/{repo}/issues/{n}/comments` с
  `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` и единственным `pull-requests: write` **сработал** — шаг
  напечатал `verdict: missing; posted a warning comment`. Документация GitHub по этому эндпоинту
  требуемых прав не перечисляет, поэтому вопрос был открыт; теперь закрыт, `issues: write` не нужен.
- **Дыра воспроизвелась на живом PR:** review от бота есть, `commit_id` равен head, тело —
  только `Automated PR review generated by OpenRabbit.`; чек `OpenRabbit Review` при этом **зелёный**
  (3м46с). То есть #87 — второй живой случай после #84, и детектор поймал его на первом же прогоне.
- **Причина внутри экшена непрозрачна, но видна снаружи:** шаг `node dist/action.js` шёл **167 секунд**
  и завершился `outcome=success;conclusion=success`. Экшен отчитывается об успехе, ничего не опубликовав, —
  ровно то, что задача и должна сделать видимым. **Поправка 2026-09-24 (задача 5.28):** разбор лога
  *успешного* прогона 35986972465 показал, что `dist/action.js` не печатает ничего **и когда публикует
  настоящий вердикт** — молчание здесь нормальное поведение экшена, а не признак проглоченной ошибки;
  сигнал существует только снаружи, в том, что опубликовано.
- **Проверка прав на удаление** (для снятия предупреждения) живой пробой не покрыта: удаление идёт по
  тому же семейству эндпоинтов issue-комментариев, что и успешный POST. Ветка покрыта стабом; при
  отказе скрипт печатает предупреждение и не падает.

## Поправка по ревью: определение вердикта

Первая версия скрипта считала вердиктом **сам факт** review бота на head SHA. Это неверно ровно на том
случае, который приведён здесь как доказательство: на PR #84 review существовал, но строки вердикта в
нём не было. Такой детектор признал бы #84 «опубликованным» и не сработал бы. Дефект нашёл
senior-review при разборе диффа (третий проход по 5.19).

Исправлено: строка `### Verdict` в теле — обязательная часть условия. Замечание «это же хрупкий
контракт» здесь не действует, потому что реакция остаётся advisory: дрейф формулировки в третьей
стороне даёт лишнее предупреждение, а не блокировку мержа. Хрупкость была бы блокером только при
`exit 1` — именно поэтому гейт и отклонён.

## Словарь исходов (зафиксирован, но не контрактуется GitHub)

| Исход шага | Когда | Поведение workflow |
|---|---|---|
| `success` | экшен вышел 0 | — |
| `failure` | в т.ч. **посменный `timeout-minutes`** (установлено в 5.15) | фолбэк запускается |
| `cancelled` | job отменён (`cancel-in-progress`) | шаги после не выполняются → часть **B** |
| `skipped` | шаг пропущен по `if` | у основного `if` нет → на практике не встречается |

Фолбэк намеренно ловит **только `failure`**: `cancelled`/`skipped` у основного шага не воспроизводимы
(при отмене job'а фолбэк не запустится всё равно), а расширение условия до `!success` тратило бы
квоту free-пула OpenRouter (50/сут) на прогон, который всё равно отменён новым push'ем. Это решение
зафиксировано ещё в 5.16 и здесь только документируется.

**Поправка 2026-09-24 (задача 5.28).** Приведённый выше отказ от `!success` больше не описывает
workflow: условие фолбэка теперь
`steps.openrouter.outcome == 'failure' || steps.primary_verdict.outputs.verdict != 'published'`.
Это **не** расширение до `!success`: проверяется не исход шага, а измеренный факт публикации вердикта,
и цена решения ложится на NVIDIA NIM (свой ключ), а не на free-пул OpenRouter — ретрай основного отклонён
именно поэтому. Смена подхода обоснована измерением: `!success` был отклонён как спекулятивное
расширение, а частота no-op оказалась 3 из 4 прогонов.

## Проверка (зонд)

Скрипт проверен против **живого** API и на стабе `gh` (10 сценариев), временный зонд не коммитится:

| Сценарий | Ожидание | Результат |
|---|---|---|
| реальные фильтры jq, верный head SHA (PR #86) | непустой id | `5300920654` |
| реальные фильтры jq, чужой SHA | пусто | пусто |
| реальные фильтры jq, **PR #84** (review был, строки вердикта нет) | пусто | пусто |
| реальные фильтры jq, **PR #84** без условия вердикта | непустой id | `5294525823` |
| реальные фильтры jq, несуществующий маркер | пусто | пусто |
| стаб: вердикт есть (тело со строкой) | `verdict: published`, без комментариев | exit 0, `[]` в логе вызовов |
| стаб: review без строки вердикта | предупреждение «опубликован без вердикта» + POST | exit 0, `POST` |
| стаб: review не опубликован | предупреждение «не опубликован вовсе» + POST | exit 0, `POST` |
| стаб: вердикта нет, комментарий есть | PATCH | exit 0, `PATCH` |
| стаб: API падает | «не проверен», без комментария | exit 0, `[]` |
| стаб: `VERDICT_ATTEMPTS=abc` | откат к дефолту, без падения | exit 0 |
| стаб: внутренний сбой (пустой `gh` в PATH) | trap → `::warning::`, exit 0 | exit 0 |

**Найденный и исправленный дефект:** первая версия скрипта использовала
`gh api --paginate --slurp ... --jq`. gh 2.96.0 **не поддерживает** `--slurp` вместе с `--jq`
(`the --slurp option is not supported with --jq`), то есть в CI шаг упал бы на первом же прогоне.
Исправлено на `--paginate` + `--jq` (gh применяет фильтр постранично) с проверкой **наличия** вывода
вместо арифметики — это корректно и на нескольких страницах. Зонд поймал бы это только на живом API,
поэтому проверка фильтров против реального ответа обязательна.

## Критерии приёмки

- [x] Финальный шаг существует, `if: always()`, без `continue-on-error` — закреплено guard-тестом.
- [x] Вердикт = review бота на текущем head SHA **со строкой `### Verdict` в теле**; пустой `commit_id` не принимается.
- [x] Предупреждение различает «опубликован без вердикта» и «не опубликован вовсе».
- [x] Retry 5×10 с; нечисловые `VERDICT_ATTEMPTS`/`VERDICT_DELAY` откатываются к дефолту; отдельная ветка «не смог прочитать».
- [x] Sticky-комментарий с маркером, содержащим SHA, и фильтром по автору; PATCH вместо дубля.
- [x] Скрипт всегда выходит 0, включая неожиданный внутренний сбой (`EXIT`-trap, установленный до разбора аргументов) — ни один путь не роняет job.
- [x] Предупреждение снимается, когда вердикт по этому head появился (иначе сигнал противоречил бы своему же совету перезапустить ревью).
- [x] Права на запись подтверждены живой пробой на PR #87: POST issue-комментария прошёл на одном `pull-requests: write`.
- [x] Guard-тест дополнительно проверяет `bash -n`: синтаксическая ошибка не доходит до trap и уронила бы обязательный чек, поэтому обязана падать в `ci:all`.
- [x] Словарь исходов зафиксирован в workflow и PRD.
- [x] Зонд: 4 живых jq-фильтра + 10 сценариев на стабе; дефект `--slurp` найден и исправлен.
- [x] `composer ci:all` зелёный (703 теста / 2043 ассерта, локальный прогон).

## Не входит в задачу

- Детекция `cancelled`/`timed_out` — часть **B** (отдельный workflow на `workflow_run`); префикс маркера
  `opencode-verdict-cancelled` зарезервирован за ней, чтобы детекторы не сталкивались.
- Триггер `reopened` — часть **C**.
- Замена строкового грепа в `ci-summary` на цикл по `needs.*.result` — задача 5.27.
- Расширение условия фолбэка до `!success` — отклонено осознанно (см. словарь исходов). **Уточнено
  2026-09-24:** задача 5.28 заменила условие фолбэка не на `!success`, а на проверку публикации вердикта
  (probe + `!= 'published'`), и оплачивает это NIM, а не free-пул.
- Права: `pull-requests: write` **подтверждён живой пробой** на PR #87 — POST issue-комментария прошёл
  на одном этом разрешении, `issues: write` не понадобился. Право на `DELETE` живой пробой не покрыто
  (идёт по тому же семейству issue-комментариев); ветка покрыта стабом, отказ репортится и шаг не роняет.
