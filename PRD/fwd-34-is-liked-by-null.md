# fwd-34 — «пользователя нет → false» переезжает в сервис

Строка Roadmap: `fwd-34`, выделена техлид-ревью fwd-7 (архитектор R3).
Оценка 0.25ч. Декомпозиция не нужна: одна атомарная правка сигнатуры.

## Проблема

После fwd-7 инвариант «у анонимного читателя нет своего лайка» выражен в двух
разных формах. В `ItemController::get:157-160` он живёт в контроллере:

```php
$user = $this->getUser();
$likedByMe = $user instanceof User && $likeService->isLikedBy($user, $item);
```

а сама сигнатура `LikeService::isLikedBy(User $owner, …)` требует не-null
объект, то есть **не выражает его вовсе**. Любой второй вызывающий, который
забудет про `instanceof`, упадёт на TypeError — а это 500, а не `false`.

`isLikedBy` — единственный вызывающий в проде, так что сегодня это
не эксплуатируется. Но инвариант, выраженный двумя формами, разъезжается: либо
контроллер проверит и забудут, либо подпись разrelaxится, и тогда второй вызов
молча решит, что аноним «лайкнул всё».

## Решение

Правило переезжает в сервис, потому что сервис — единственное место, где оно
обязано выполняться для любого вызова:

```php
public function isLikedBy(?User $owner, Item $item): bool
{
    if (!$owner instanceof User) {
        return false;
    }

    return $this->findLike($owner, $item) instanceof Like;
}
```

Форма в блоке — итоговая, принятая под давлением `rector:dry-run`; см. «Конфликт
двух инструментов» ниже. Первым кандидатом был `null === $owner`.

Контроллер схлопывается до одного вызова. `instanceof User` в нём **остаётся** и
не является «второй формой правила»: `getUser()` возвращает
`?SymfonyUserInterface` (контракт фреймворка), а сервис ждёт доменный
`App\Domain\User\Entity\User`. Снять проверку нельзя — PHPStan со strict-типами
это поймает, и правильно.

## Чего не делаем

- **Не** заводим `viewer(): ?User` в `AbstractApiController`: у такого хелпера
  был бы ровно один вызывающий — это абстракция ради абстракции (техлид и
  архитектор независимо указали).
- **Не** трогаем `getUser()` и файрвол. Гостевая ветка деталки уже проверена
  `GuestReadTest::testGuestCanReadOneItemWithFalseLikedByMe` — поведение не
  меняется, байт в байт.
- **Не** меняем OpenAPI: контракт ответа прежний, `liked_by_me` остаётся
  `boolean`.

## Тест-стратегия

`testIsLikedByFalseWhenOwnerIsNull` с репозиторием-моком, который
`expects($this->never())->method('findByOwnerAndItem')`. Это важно: если бы
мок просто вернул `null`, тест прошёл бы и при наличии запроса — то есть
проверял бы не то. `never()` доказывает, что сервис **не ходит в базу** вообще,
а не просто вернул false.

Два существующих теста (`testIsLikedByTrueWhenLiked`,
`testIsLikedByFalseWhenNotLiked`) не меняются — они и есть защита от регрессии
для не-null ветки.

## Конфликт двух инструментов, разрешённый в коде

Первый вариант был `if (null === $owner)`, по сквозной конвенции проекта (12 мест
Yoda-стиля). `rector:dry-run` его отверг: `FlipTypeControlToUseExclusiveTypeRector`
для nullable **объекта** всегда требует `!$owner instanceof User`. Это не новое
правило, а первое в проекте nullable-объектное сравнение — поэтому и не
поймано раньше.

Сквозная конвенция здесь проигрывает, и это правильно: правило rector'а
не применяется к скалярам (поэтому `null === $name` в `ItemService` жив), а к
объектам оно требует форму, которая выражает **тип**, а не сравнение с
`null`. Формулировка «это не наш User» честнее, чем «это null», потому что
формально параметр допускает ровно два значения.

`skip` в `rector.php` не понадобился: `!$owner instanceof User` с уже
импортированным `User` устраивает и rector, и php-cs-fixer (проверено обоими).
