# 10.18 — Фолбэк-модель NIM снята с производства

## Дефект

`OpenRabbit Review` — обязательный чек. Его фолбэк ходит в NVIDIA NIM с моделью `openai/gpt-oss-20b`. 2026-11-18 NVIDIA сняла её с производства, и API отвечает:

```
410 Gone: The model 'openai/gpt-oss-20b' has reached its end of life
on 2026-11-18T08:00:00Z and is no longer available.
```

Пока основной провайдер (OpenRouter free) публикует вердикт, чек зелёный. Но когда публикации нет — а это штатный режим free-пула — запускается фолбэк, падает на 410 и роняет обязательный чек. На PR #196 воспроизведено дважды подряд, то есть не флак.

## Решение

`llm_model` фолбэка → **`z-ai/glm-5.3-flash`**.

Модель выбрана по живому каталогу, а не по памяти: `GET https://integrate.api.nvidia.com/v1/models` (доступен без ключа) отдаёт 32 модели, `openai/gpt-oss-*` в нём отсутствует, `z-ai/glm-5.3-flash` присутствует. Выбор владельца — GLM-5.3-Flash; в каталоге также есть `minimaxai/minimax-m3.1-flash`, `moonshotai/kimi-k3.1-pro`, `mistralai/mistral-large-4-1t-a52b`, `nvidia/nemotron-3-ultra-550b-a55b`.

Пин в `CodeReviewConfigTest` обновлён и получил сообщение, объясняющее, зачем он: молчаливая подмена модели или устаревший пин должны требовать осознанной правки. В workflow добавлен комментарий с процедурой на случай следующего 410 — открыть каталог, выбрать chat/completions-модель и обновить оба места: workflow и пин в тесте.

**Непроверяемое без ключа:** каталог для `z-ai/glm-5.3-flash` отдаёт только `id`/`owned_by`, без флагов `supports_thinking`/`supports_tools`, которые есть у части моделей. Экшен передаёт `reasoning_effort`, и совместимость параметров подтверждается только живым прогоном — это и есть acceptance-пункт ниже. Если модель отвергнет параметр, фолбэк снова покраснеет, и следующий кандидат — `minimaxai/minimax-m3.1-flash`.

## Почему не гейтящая автопроверка

Проверять живость модели на каждом прогоне — сетевой вызов в CI, который сам может упасть и покраснить чек. Ретраи и фолбэк-на-фолбэк раздувают бюджет job'а (сейчас 35 минут, худший путь 32). Модели меняются раз в месяцы, а не в каждом PR, поэтому ручной пин с записанной процедурой дешевле и предсказуемее.

**Отдельно про advisory-автоматику:** в проекте уже есть `dependency-drift.yml` — еженедельный cron, который только печатает `::warning::` и всегда выходит с нулём, то есть в гейт не входит. Расширить `scripts/check-tool-version-drift.sh` проверкой каталога NIM — законный follow-up: он поймал бы следующий 410 **до** того, как обязательный чек покраснеет. Это не сделано здесь, потому что требует своей инфраструктуры (парсинг каталога, список допустимых чат-моделей) и не блокирует восстановление; отдельная задача при следующем инциденте или по желанию.
