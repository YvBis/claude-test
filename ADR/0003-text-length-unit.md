# ADR 0003 — Единица измерения длины текста: Unicode code points

**Статус:** принято (2026-10-19, задача `review-17`)

## Контекст

Длины текстовых полей ограничены в двух местах: домен (value objects и сущности) и контракт
API (`Assert\Length` в Application DTO + `maxLength` в OpenAPI). Symfony Validator измеряет
длину в **Unicode code points**: `Length` по умолчанию `charset: 'UTF-8'` и
`countUnit: COUNT_CODEPOINTS` (`vendor/symfony/validator/Constraints/Length.php:55,59`),
а валидатор считает `mb_strlen($value, $charset)`
(`Constraints/LengthValidator.php:56`).

Домен же исторически мерил байтами (`\strlen`). На ASCII разницы нет, поэтому расхождение
жило незамеченным до `review-17`: имя коллекции из 60 кириллических символов — это 60 code
points (DTO и опубликованный контракт его принимают) и 120 байт UTF-8 (домен его отвергал).
Исключение не переводилось ни в один HTTP-статус и клиент получал 500 вместо 201.

## Решение

**Длина текста в домене измеряется в Unicode code points — той же функцией и с тем же
charset, что у контракта: `mb_strlen($value, 'UTF-8')`.**

Явно отвергнутые альтернативы:

- **Grapheme clusters (`grapheme_strlen`).** Более «человечная» единица, но она расходится
  с контрактом: 21 последовательность семейного эмодзи (ZWJ) — это 21 графема и 105 code
  points, поэтому grapheme-граница приняла бы то, что `Assert\Length` отвергает, то есть
  воспроизвела бы исходный дефект зеркально. Механический страж — тест
  `CollectionNameTest::testFromStringRejectsZwjSequenceOverMaxCodePoints`.
- **Нормализация Unicode (NFC/NFD).** Не выполняется ни на одной стороне: `'é'` в NFD — два
  code points и там, и там, так что parity сохраняется. Введение нормализации изменило бы
  хранимые значения — это отдельное продуктовое решение, а не выравнивание единицы.
- **Общий примитив `TextLength`.** Не вводится: это однострочный идиом с единицей,
  принадлежащей вендору, а не логика. Реальное принуждение обеспечивает guard-тест, а не
  форма вызова.

**Область действия:** `src` целиком, не только `src/Domain` — контракт живёт в Application
DTO и Infrastructure OA, поэтому guard сканирует весь `src` на `strlen(` с allowlist,
где каждая запись обязана нести причину.

**Разрешённые байтовые проверки:** `UuidBinaryValue` (16 бинарных байт — контракт типа,
не текст) и `PasswordHash` (минимум plain-пароля; вопрос code-point parity решается в
`review-15` вместе с усечением bcrypt на 72 байтах).

## Последствия

- Домен принимает ровно то, что обещает контракт: 100 code points, до 400 байт UTF-8.
  Колонки `VARCHAR(100)` под `utf8mb4` считают символы, поэтому схема не меняется.
- Сообщения об ошибках не менялись: они уже говорили «characters», то есть совпадали с
  новой семантикой, пока код мерил байты.
- `InvalidArgumentException` из домена по-прежнему не транслируется в 4xx — это отдельный
  класс (`review-18`), а не часть единицы измерения.

## Что заставит пересмотреть

1. Контракт перестанет считать code points (смена `countUnit`/charset у `Assert\Length` или
   переход на другую валидацию) — тогда двигать домен за контрактом.
2. Появится продуктовое требование ограничивать длину по графемам (например, «не больше 100
   видимых символов» для UI) — тогда нормализация и `grapheme_strlen` вводятся осознанно и
   сразу по обе стороны, вместе с тестом-стражем на расхождение.
3. Понадобится хранить нормализованные значения (поиск, дедупликация) — это решение о
   нормализации, и оно потянет за собой миграцию данных.
